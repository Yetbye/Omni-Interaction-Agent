第一章 · PLUGIN TREE

无特权内核的插件树

DSH 文档把它的架构哲学写成一句话：「无特权内核，一切皆插件、皆可 patch 替换」。 这不是修辞——它决定了 OIA 这条二开线能否不 fork 内核地做出完整产品（本报告 §0 执行摘要的第一条结论）。

1.1 为什么「没有特权内核」反而让二次开发变简单

常规思路是：内核不可动，扩展靠预留钩子。DSH 走的是 Cordis 插件树路线——产品每一部分都是插件： 模型适配器是插件、工具注册表是插件、会话日志与投影是插件，连 agent loop 本身也是插件。 插件的生命周期语义极其干脆：注册即副作用、卸载即撤销。没有一段「只有内核才能改」的隐秘状态， 于是二次开发的动作退化成两个动词——装（insert）与改（按 id 定位替换）。

代价也很直白：没有「官方后门」可用，任何行为都必须用插件注册与 patch 表达； 调试的对象从「读内核源码」变成「看插件树拼装结果」；而被你替换掉的 provider， 其一致性责任随之转移到你身上（例如会话日志的 CAS 修订协议）。 替代方案有三条：① fork 内核（升级即漂移，被 OIA 明令禁止，只保留「最小 patch 分支 + 可 rebase」兜底）； ② monkey-patch 运行时（不可审计、不可下钻，与「白盒可追溯」的产品要求冲突）； ③ 外挂网关在 harness 之外改写流量（正是第三方接入文档展示的思路，代价是看不见会话内部事件）。 DSH 选择 ① 的反面：把一切变成可组合的树。

1.2 三层组装：profile → bundle → home patch → --patch overlay

插件树不是手拼的，而是分层配置叠出来的（本报告 §2 记为 profile + bundle + 分层 cordis.patch.yml）：

  • profile 列 bundle——profile（如 omni）声明本实例加载哪些组合包（如 @omni/omni-base）；
  • bundle patch——每个组合包自带自己的 cordis.patch.yml，声明它要插入/替换的条目；
  • home patch——DSH_HOME 级别的 patch（OIA 即 ~\.omni-dsh 下的配置），覆盖到该 home 的所有会话；
  • --patch overlay——命令行显式追加的一次性覆盖层，优先级最高，用于实验与验收（dsh --profile omni --dump-config 就是看这四层叠加后的最终树）。

patch 的语义只有两种，且都按 id 定位：替换整条 config（同 id 的条目整条换掉，不做字段级魔法合并）， 或插入一条新条目。这条纪律看似粗，实则把「改了什么」变成可 diff、可回滚、可审计的文本—— 正是隔离验收清单第 ② 条（组合树中不含任何 @omni 之外的自研条目）能机械检查的原因。

洞察

「无特权内核」的工程红利：二开 = 叠加，不是分叉

因为连 agent loop 都是插件，OIA 的全部自研内容都能落在组合包 + patch 层这两个纯增量位置上。 上游更新时，我们的树只是「重新拼一次」，而不是「合并一次冲突」。这正是本报告 §2.2 所说的： DSH 文档推荐的扩展方式就是「新行为附加到已有文档记录的扩展点」。

来源：report.html §0 / §1.2 / §2.1（已核验本机安装版内核文档 architecture / capability-seams）。

证据

第三方记忆已经证明这条路通：腾讯云 DSH 接入文档

本机存档的 TencentDB 官方 DSH 接入文档（docs/sources/tencent-dsh-adapter.md）显示： dsh v0.2+ 的配置入口就是 ~/.dsh/profiles/<profile>/cordis.patch.yml（loader patch 数组）， 插件以 - id: … / name: "@deepseek-ai/…" 条目形式写入，凭据单独放 .credentials.yaml 的 refs: 段； 记忆侧则把 <user_memory>、<tdai_profile_memory> 等标签追加到请求 system 段、并复用原生 ask_user_question 工具做会话初始化。整套接入没有 fork 任何一行内核—— 这是「DSH 生态可接第三方记忆」的现成实证，也是 OIA 插件族要复用的同一形态。

来源：docs/sources/tencent-dsh-adapter.md §1.1 / §6；report.html §4.1。

CHAPTER 2 · THREE THESES

三大命题的原生落点

Delegation（委托）、Proactivity（主动性）、Consistency（一致性）是本系列反复出现的三大命题。 选型阶段最重要的发现是：它们在 DSH 里不是三个待实现的需求，而是三群已文档化的 seam （本报告 §2.2：subagent+teams / schedule+goals / session-log+projections 三大 seam 群，一一命中）。

2.1 Delegation：subagent seam × Agent Teams × workflow

  • subagent seam：spawn / fork 两种派生方式，多 provider（ACP / Codex / Claude Code / DSH SDK）， 统一 activation 生命周期、深度限制、树内消息 / 中断 / 收件箱等待。OIA 的观察者（Observer）、记忆员由此直接成形。
  • Agent Teams 任务板：共享任务板带 owner / CAS 修订 / 阻塞依赖 / 写域（write scope，advisory）—— 多代理协作的一致性与写冲突预防是现成协议，不用自创锁。
  • workflow 编排：模型写编排脚本，agent() / pipeline() / parallel() 扇出，fatal 错误纪律明确； 对应 Omni-IO 的执行图（本报告 §7）。

为什么把委托交给 seam 而不是自建调度：代价是必须接受 harness 的生命周期语义（激活、中断、深度上限都由它裁决）， 回报是树内消息、中断与任务板的并发语义免费获得；替代方案是进程外编排（如外部工作流引擎）， 但那样跨代理的会话事实源会分裂，违反一致性底座。

2.2 Proactivity：宿主级 Schedule × Goals × webhook

  • Schedule（宿主级，不依赖会话存活）：七种时间类型（after / at / every / daily / weekly / cron / rrule）、 可投递到现有 / 预留 / 全新会话；停机期间只追赶最新一次（不补一堆重复触发）；60s 最小间隔。
  • Goals：事件溯源的目标 + 轮次预算 + blocked 理由码 + 激活边沿（armed / disarmed）—— 长程任务的「有界主动」，既会自动续跑，又天然可停。
  • webhook 运行时：外部事件（消息 / 设备 / 日历）直接启动会话，作为主动入口。

为什么用宿主级时基：主动性最容易犯的错是「挂在某个会话里等会话活着」。 代价：调度语义归宿主，插件不能随意改写触发规则（只能用其时间类型表达）； 替代方案：进程内 setTimeout / 外部 cron——前者随进程消失，后者拿不到投递目标，也进不了会话日志。

2.3 Consistency：会话日志唯一事实源 × 投影 seam × CAS

  • 会话日志 = 唯一事实源：核心不变量是「模型可见即已记录」——模型看到的每一段上下文都已经写进日志； deriveMessages 投影出模型历史，fork / 恢复 / 导出 / 遥测全部从日志派生；格式带 v0→v4 迁移链。
  • 投影 seam + CAS 修订：goals / schedule 的更新要带 expectedRevision / expectedUpdatedAt， 并发写冲突被协议化而不是靠运气。

为什么一致性排到最后讲却最重要：记忆、委托、主动行为只要都落日志，就可回放、可审计。 代价是任何绕过日志的「暗写」都会破坏不变量；替代方案是应用层自建状态库—— 那会造出第二个事实源，正是 savepoint 门户「状态 = 事件折叠」思想（本报告 §1.3）要避免的分裂。

洞察

「模型可见即已记录」是记忆系统的宪法

只要召回结果必须经 agent.inject() / agent/pre-step 进入模型上下文， 它就自动进了会话日志——于是「这次回答被哪条记忆影响」天然可追溯（MemoraX 式影响披露的数据源）， 干预决策也一样。反过来推论：任何绕过 seam 的暗写（直接改消息数组）都会同时破坏一致性与可审计性， 在 OIA 里应视为 bug 而非捷径。

来源：report.html §5.1 / §2.3 / §8.1（内核文档 capability-seams / session）。

代价清单

原生落点不等于免费

① 注入有预算：召回条目必须受上下文预算约束，否则记忆越全、上下文越爆（CAMEL 的预算×分数组装思路，本报告 §8.2 #10）。 ② 事件有粒度：agent/turn-stopping 是轮次级钩子，「轮次结束才蒸馏」意味着流式中途的半句话不会被写回—— 需要即时性时得另找 session/event 消费点。③ CAS 要带版本：并发写必须携带 expectedRevision， 忘带就退回「最后写者赢」。④ 调度语义归宿主：60s 最小间隔与「停机只追赶最新一次」不可绕过， 想做秒级高频轮询只能换机制。

CHAPTER 3 · PI AS SUPPLY

Pi 生态的补给位

Pi（pi-mono）是另一条候选路线：一个极简、可完全自定义的 agent harness—— 「Adapt Pi to your workflows, not the other way around」。它没被选为主基座，却在三个位置持续给 OIA 供货。

3.1 Pi 是什么（README 已读部分）

  • 扩展四件套 + 包模型：extensions / skills / prompt templates / themes，打包为 Pi packages， 通过 npm 或 git 分发——「包即插即用」的分发哲学。
  • chord 对象运行时（@earendil-works/chord）：跨进程的对象运行时，含契约、文档、存储、链接、 带热重载的插件、HTTP、workers、web 与终端客户端。
  • pi-ai：统一多 provider LLM API（OpenAI / Anthropic / Google 等）； pi-durable 提供持久会话 / 任务 / 文档运行时；另有 pi-agent-core、pi-tui、telemetry 等包。
  • 自动化与集成面：交互式、print / JSON 模式、RPC 控制、TypeScript SDK（OpenClaw 是其真实集成案例）。
  • 关键事实：DSH 已内置 dsh-llm-pi-ai 适配包——Pi 的 LLM 层已经在 DSH 里跑着，两者天然可组合。

为什么结论是「DSH 主基座、Pi 补给」：OIA 的三大命题在 DSH 侧全部有原生 seam， 而 Pi 侧的委托与主动性要从零造，一致性只有运行时库而没有「唯一事实源 + 迁移链」的纪律， 安全还要自备容器。代价是接受 DSH 更重的插件体系与更快的版本演进（当前安装 0.2.2-rc.3 系，需按 upgrade-guide 固定 upstream）； 替代方案是把 Pi 当主基座、用其 packages 拼一个最小产品——对「实时交互全模态智能体」而言， 事件溯源会话日志是刚需，自建这条底座的成本远高于学习 DSH 的 patch 体系。

3.3 Pi 作为补给的三个具体位置

  • ① LLM 层：pi-ai 已通过 dsh-llm-pi-ai 进入 DSH，Omni 多模态模型接入优先扩这条适配线 （注意接入文档的教训：pi-ai 适配器会过滤掉 x-deepseek-harness-* 系列头，走自定义卡时要清楚其副作用）；
  • ② 包模型：extensions / skills / prompt-templates / packages 的划分，作为 @omni/* 包设计的对照参考 （本篇代码附录的打包范本即按此精神裁剪）；
  • ③ 集成面：Pi 的 RPC / SDK / JSON 模式启发 OIA 的 headless 集成设计。

反面提醒

Pi 侧的两个「默认没有」会咬人

① 默认无 sub-agents 与 plan mode——如果误把 Pi 当主基座，Delegation 整章要重写； ② 无内置权限系统——Pi 默认以启动它的用户与进程权限运行文件系统 / 进程 / 网络 / 凭据访问， 官方给的三种边界（Gondolin 微虚机、Docker、OpenShell）都是进程外方案。 对要采集桌面观察流的 OIA Observer 来说，权限边界必须一等设计，这条差异是决定性的。

CHAPTER 4 · ISOLATION RED LINES

OIA 总体设计与五层隔离红线

回到概念框架：四支柱（记忆 / 委托 / 主动性 / 个性化）+ 一个底座（一致性与全模态 IO）。 本章把它落成两样东西：五组件的挂载表与五层隔离红线。

4.1 四支柱 + 底座的回顾

本报告 §3 给出的框架是：① 记忆 Memory（分层金字塔 · 符号画布 · 白盒治理）、② 委托 Delegation（子代理树 · 团队任务板 · 工作流）、 ③ 主动性 Proactivity（观察者 · 干预时机 · 沉默与追问）、④ 个性化 Personalization（画像 · 表达规划 · 隐式反馈适应）， 底座是会话事件日志（唯一事实源）· 投影 · CAS 修订 · 技能/资产注册表 · 全模态执行图。 前三支柱在上一章已各自落到 seam；本章处理记忆支柱的五组件与整体边界。

4.2 五层隔离红线

层隔离手段具体约定
代码独立目录 + 独立 git 线 仅 omni-interaction-agent/ 门户；以 deepseek-harness 开源仓库为 upstream， 自研内容全放 @omni/* 组合包与 patch 层，尽量不改内核；必须改时走「最小 patch 分支 + 可 rebase」
运行时独立 DSH_HOME 与 profile DSH_HOME=%USERPROFILE%\.omni-dsh；profile 命名 omni（组合包 @omni/omni-base）； 端口与 IPC 独立（web 端口 8848 起），与日常 Desktop 不冲突
插件命名空间与安装事务隔离 插件 id 一律 @omni/…，不复用 @deepseek-ai/…；禁止向 ~\.dsh\profiles\desktop 安装/启用任何 OIA 插件
数据独立记忆库与会话日志 记忆库 ~\.omni-dsh\memory\（SQLite + 附件区）；会话 JSONL 同落 OIA 自己的 home，与 ~\.dsh 无读写交集
工作区独立门户目录 仅 omni-interaction-agent/ 一个入口；不 import、不复制、不改动其余五个项目门户的任何文件

洞察

隔离既是工程约束，也是产品需求

两重理由：其一，日常 Desktop 承载研发，绝不能被 OIA 的实验性组合包、HMR 重载、插件安装事务波及； 其二，OIA 将来作为独立产品分发，必须自带运行时边界——隔离不是临时护栏，而是交付形态的一部分。 五层红线里最容易被忽视的是插件层：home 分开了但插件 id 混用，安装事务仍可能互相污染，所以 @omni/* 命名空间与「禁装日常 profile」是硬规则而非风格偏好。

来源：report.html §1.1 / §1.2。

代价与替代

双实例的维护税

代价：两套 home 意味着双份配置、双份升级、双份凭据管理，版本还可能漂移（当前安装 0.2.2-rc.3 系， 二开线需固定 upstream 版本、按 upgrade-guide 迁移，禁止跟踪 unstable）。 替代方案：同一 DSH 多 profile 省一半运维——但数据层（记忆库、会话 JSONL）与插件安装事务仍共享 home， 达不到「数据零交集」的验收第 ④ 条。权衡结论：宁可付双实例的运维成本，也要保住数据与插件两条红线； 缓解手段是把 OIA 侧全部配置收敛进 @omni/* 组合包，让升级动作退化为「重拼一次树」。

来源：report.html §1.2 / §10 风险登记（DSH 版本演进快）。

plugin '@omni/memory-recall' {

               intent = 'auto',

CHAPTER 6 · OPEN QUESTION

延伸问题：seam 的边界在哪里

收官不收口。下面这个问题，决定了 OIA 未来所有「深度定制」需求的处理纪律。

延伸研究问题

在不 fork 内核的约束下，深度定制的理论上限在哪里？

理论分析：能力 seam 的覆盖度给出了一个清晰的上限——凡是被文档化的扩展点 （Definition / Provider / Consumer 三角色所及之处），都可以不 fork 地整条替换： 换 ctx.llm 的 provider 即换模型接入，换 compaction 后端即换符号画布，换 subagent provider 即换子代理实现。 但循环语义本身由 agent-loop 拥有——step 如何推进、turn 何时结束、日志何时落盘的编排次序， 是 seam 之间的「胶水」，不是 seam 自身。seam 之外的需求只有两条路：找一个语义相近的扩展点绕行， 或者落进最小 patch 分支。后者可以形式化为一个可维护性指标：

Rrebase = Lpatch × fupstream （patch 行数 × 上游变更频率）
R 越小，上游升级时的合并成本越低；理想态是 L→0（全走 seam）。

研究方向：做一次seam 覆盖度审计——枚举 OIA 需要的全部行为 （记忆写回、召回注入、上下文卸载、跨会话检索、观察者派生、干预调度、任务板并发、治理面板）， 逐条判定它落在哪个已文档化扩展点，统计 L_patch 的初始值与高危行 （触及 agent-loop 次序的行）；此后每个上游版本按 R_rebase 重估一次， 把「何时必须放弃某条 patch」从直觉变成数字。配套问题是：能否把「模型可见即已记录」 做成一条可执行的一致性测试（对任意注入路径断言日志可回放），作为 CI 门禁防止暗写回潮。

系列回顾：篇 1–4 给出记忆五组件的证据与代码级来源，篇 5 给出主动性与个性化的行为设计， 本篇把它们全部挂回 DSH 的能力 seam，并用五层红线把运行时圈起来—— 下一步是 M1：独立 DSH_HOME + profile omni + @omni/memory-vault + T0 词法召回 + 写回钩子。
