CHAPTER 01

记忆为什么不能是「平的」

TencentDB-Agent-Memory 的 README 用了一个很重的词来描述业界现状：传统记忆系统把数据切碎、 扔进一个扁平向量堆，于是「召回退化为在互不关联的碎片里做盲搜，没有任何宏观层面的引导」。 这不是修辞——它精确指出了向量检索的结构性缺陷：相似度只度量邻近，不携带结构。

扁平堆的三宗罪

  • 碎片切断了上下文：一条事实被切块入库后，它属于哪次任务、哪个人格、哪个场景的元信息随之丢失； 命中了也不知道能不能用。
  • 检索退化为盲搜：每次查询都要在 |D| 个候选碎片上全量打分，没有「先看哪一层」的先验， 宏观问题（「我是个什么样的用户」）被迫用微观手段（向量近邻）去回答。
  • 压缩与取证互斥：要省 token 就摘要，摘要就丢证据；要保证据就全塞，上下文就爆。 扁平结构里这两者是零和的。

「上层结构、下层证据」的哲学

该项目把形成（formation）与召回（recall）都做成层级化，并给出一句可作为设计宪法的话： 「下层保存证据，上层保存结构」（Lower layers preserve evidence; upper layers preserve structure）。 底层（事实、日志、轨迹）进数据库以获得可靠的全文检索；顶层（人格、场景、画布）存成人可读的 Markdown， 换取高信息密度与白盒可检视性。它同时明确拒绝两个极端：野蛮的历史堆砌与 不可逆的有损摘要——两者都被写进了 Overview。

维度扁平向量堆分层语义金字塔
存储形态同构碎片 + 单一向量索引异构：底层数据库、顶层人可读 Markdown
检索方式全量相似度盲搜先定位层，再沿下钻链取证（渐进披露）
结构先验无：相似 ≠ 相关有：层级即「先看什么」的路由表
压缩可逆性摘要即终点，丢证据不可恢复抽象层必有损，但保有回到底层的确定性路径
上下文成本要么全注入、要么赌命中上层结构只占少量 token，细节按需下钻
调试方式一串向量分数，无从定位错误打开文件沿链走：白盒

替代方案对比：为什么不是纯 RAG、不是全量注入

纯 RAG（切块 + 向量检索）：写入成本最低，但只解决「找回相似片段」，不解决「这个片段属于哪个任务的哪一步」。 对长程工作负载，命中孤立片段的边际价值很低——你仍然要靠模型自己重新拼装语境。
全量注入（不压缩）：证据最完备，但 README 指出长任务里最大的 token 消耗者恰恰是 冗长的中间日志（搜索结果、代码、错误堆栈），全量注入等于把预算烧在噪声上。
不可逆摘要：省 token，但一旦摘要出错或过时，原始证据不可恢复——该项目明确把「可恢复性」当硬约束， 要求从高层抽象到地面真值始终保持一条确定性路径。

Cflat = Θ( |D| · cmatch ) ， Clayer = Θ( |Stop| · cmatch + h · cref ) ， |Stop| ≪ |D| 且 h ≤ 3
直觉：扁平方案的探测成本随碎片数线性增长且无先验剪枝；分层方案先在极小的顶层结构上定位， 再走一条长度有界（金字塔只有四层）的下钻链取证——代价从「搜遍」变成「沿边行走」。
深度洞察

结构不是画给投资人看的架构图，而是检索的先验

分层的真正收益不在于「数据被组织得好看」，而在于它把查询路由做成了免费的： 面对宏观问题先看 L3/L2，面对细节问题直接下钻 L1/L0，面对进行中的任务先看画布。 每一层都是一张为特定问题类型预建的索引——扁平堆里这张索引不存在，只能靠每次查询临时重建。

批判评估：分层不是免费的。写入路径必须持续跑 LLM 抽取（token 成本 + 延迟）， 层与层之间要维护一致性（persona 由哪些 scenario 生成、scenario 何时该合并）；而扁平堆唯一的优点正是 写入零成本。所以「分层是否划算」取决于一个不等式：读多写少、且错误召回代价高时分层占优。 该项目把 benchmark 全部压在连续长程会话上（例如 SWE-bench 每个 session 连续跑 50 个任务， 模拟真实长程 agent 的上下文积累压力——README 自述的测试设定 自报·未复现）， 正是为了让这个不等式在它的主场成立。换到短对话、高频写入的场景，结论未必一样。

CHAPTER 02

L0→L3 语义金字塔与确定性下钻

长期记忆侧的分层被具体化为一座语义金字塔： L0 Conversation（原始对话）→ L1 Atom（原子事实）→ L2 Scenario（场景块）→ L3 Persona（用户画像）。 注意这不是四个数据库表的委婉说法，而是四种不同的信息形态：从「逐字记录」到「独立成句的事实」 到「有主题的情境块」到「跨情境稳定的画像」，每上一层，抽象度升高、体积缩小、可读性增强。

金字塔同时管「知识」与「技能」

README 把同一范式推广到动作层：底层是执行轨迹（Conversation），中层从中归纳出通用解法模式（Scenario）， 顶层蒸馏为可复用的 Skill 或标准 SOP（Persona 层）。架构洞察：知识分层与技能分层共用同一条 「从证据到结构」的上升通道，意味着抽取管线、去重规则与下钻机制可以复用——这是把分层做成 统一架构范式（unified architectural paradigm）而非局部技巧的真正动机。

问题类型先看哪一层下钻到哪一层
日常偏好、语气、长期目标L3 Persona / L2 Scenario需要事实时下钻 L1 Atom / L0 Conversation
具体事实、日期、项目细节L1 Atom / L0 Conversation结果稀疏时扩大时间范围，或回退语义召回
续接进行中的长任务活跃 Mermaid 任务画布摘要不够细看 JSONL，再进 refs/*.md 读原文
恢复历史任务元数据任务入口打开画布 → 定位 node_id → 追 result_ref

（表转述自 README「Macro Personas + Micro Facts」的下钻表；refs/*.md、node_id、result_ref 为项目自有标识。）

异构存储的 rationale：为什么底层进数据库、顶层存 Markdown

设计 rationale：底层（L0/L1）的访问模式是高频、条件化、大规模的—— 按类型过滤、按时间范围扫、按关键词倒排、按向量近邻，这正是关系型 + 全文/向量索引的主场 （源码里是 l1_records 配 FTS5 虚表与 sqlite-vec 的 vec0 虚表，BM25 + 向量 + RRF 混合检索）。 顶层（L2/L3）的访问模式是低频、整读、人机共览的——画像和场景块是要被「打开看一眼」的， Markdown 的信息密度、可 diff 性、可手工编辑性完胜数据库行。
替代方案对比：全存数据库 → 人无法直接检视，白盒承诺落空；全存 Markdown → L0/L1 规模上来后检索性能与条件过滤崩塌。每一层用对工具，才是「异构」二字的全部理由。

深度洞察

白盒调试 = 沿链行走，而不是在黑箱里捞分数

README 对现状的批评很尖锐：多数记忆系统召回出错时，你看到的只有一串向量分数，无从判断错在哪一环。 这里把关键中间产物全部落成可读文件——L2 场景块是纯 Markdown、L3 画像住在 persona.md 并可回溯到生成它的场景、画布是 Mermaid、原始载荷/摘要/节点由 result_ref 与 node_id 串联。 调试因此变成一次确定性行走：Persona → Scenario → Atom → Conversation， 走到哪一层发现断裂，根因就在哪一层。所有分层产物都躺在 ~/.openclaw/memory-tdai/ 下， 项目甚至鼓励你直接打开目录逐层检查。

H( E | A ) > 0 （抽象必然有损：证据 E 相对抽象 A 有条件熵）
保存映射 π : A → E ， 使 H( E | A, π ) = 0 （在可下钻意义上无损）
压缩本身不可消除信息损失；可消除的是「损失的不可恢复性」——只要每一层抽象都携带一条回到底层证据的确定性映射， 摘要出错时就还有退路。这正是「拒绝不可逆有损摘要」的数学表述。

跨文连接：这座金字塔的对立面是 rolling-memory 的「原文档案铁律」—— 它拒绝任何 LLM 在入库时改写/摘要历史，理由是「用可能幻觉的模型去改写可能被误解的对话是错误复合」。 两个方案是同一根光谱的两端：一端允许蒸馏但强制保下钻链，另一端干脆不蒸馏。 OIA 的取法是中间路线——蒸馏照做，但额外要求被取代的旧措辞保留为 superseded 历史（MemoraX/续忆一系的要求）， 即把「留痕」从链路级（本项目的下钻）细化到措辞级。

批判评估：下钻链的可靠性完全取决于上游抽取质量： 如果 L1 原子事实本身就抽错了，L3 画像会把错误稳定化，而「白盒」只能让你更快地发现错误、不能阻止错误。 此外，链是单向构造的（由下往上蒸馏）而双向使用（由上往下取证）——每次下钻都是一次额外的读放大， 预算没有写明每层最多下钻几次、失败后如何降级（README 只给了「结果稀疏时扩大时间范围或回退语义召回」的策略）。

CHAPTER 03

短期符号画布：offload → node_id → refs

如果说长期记忆解决「跨会话记住你」，符号画布解决的是「本次任务别被日志淹死」。 README 的判断是：长任务里最大的 token 消耗者是冗长的中间日志（搜索结果、代码、错误堆栈）。 对策是三层卸载：底层把原始工具输出全文卸载到 refs/*.md；中层在 offload.jsonl 里留步骤级摘要；顶层把任务状态压成一张轻量的 Mermaid 符号图。上下文里只留顶层结构， 出错时凭 node_id 下钻取全文。

数据形态：一条 offload 条目长什么样

每条被卸载的工具调用在 offload.jsonl 里是一行 JSON：timestamp（继承自原始工具结果）、 node_id（L2 分配的 Mermaid 节点号，运行前为 null）、tool_call（命令简述）、 summary（LLM 生成的结果摘要）、result_ref（指向 refs/*.md 全文的相对路径）、 tool_call_id、session_key，以及一个值得注意的字段—— score（0–10 的可替代性评分：摘要多大程度上能替代原文，由 L1 的 LLM 打分）。 架构洞察：可替代性评分把「哪些日志可以先扔」从启发式变成了可排序的决策： 分数越高越先卸载——这与后续 mild/aggressive 两档压缩的分批策略是同一套思路。

L2 触发：阈值 4、超时 300 秒与 wait 态

L2（画布生成）不再由 L1 直接触发，而是独立运行，有两个触发条件（源码头注释原文）： 条件 A：offload.jsonl 中 node_id=null 的条目 ≥ l2NullThreshold（默认 4）； 条件 B：距上次 L2 超过 l2TimeoutSeconds（默认 300 秒），且默认要求确实存在比上次 L2 更新的空节点行（避免对陈旧数据空转）。
失败路径：如果 L2 解析/映射失败，条目会被留在 node_id="wait" 态， 至少等待 l2WaitRetrySeconds（默认 120 秒）后重试，另有 backfillNodeIds 负责回填。 设计 rationale：「4 条」是一个延迟与压缩率的折中常数——攒太少， 每次画布更新都太贵；攒太多，上下文里长期躺着过时的结构。这个数没有公开消融，属于经验值。

注入模板原文（mmd-injector.ts）：
【当前活跃任务的mermaid流程图】这是你最近正在执行的任务的阶段性记录（此条下方的tool use未被汇总，进程可能有延迟，仅供参考）。
节点索引: 可通过 node_id 在 offload.{sessionid}.jsonl 中查找对应的工具调用记录。 如需查看某个节点对应的原始工具调用与完整结果，请在 offload.{sessionid}.jsonl 中找到对应条目的 result_ref 并读取该文件。
末尾还有状态语义：标记为 "doing" 的节点是近期焦点，"done" 的已完成——「请参考此保持方向感，避免重复已完成的工作」。

设计 rationale：这段模板是「压缩不牺牲证据链」的落点：它不只注入图， 还把下钻协议一起注入——告诉模型 node_id → jsonl → result_ref → 原文这条查找路径， 等于每次注入都重申一次取证说明书。配套的 L2 提示词纪律同样严格： 「只记录已发生、未发生不写、每个节点标注 node_id 来源」，防止画布变成模型的臆测流程图。

深度洞察

压缩不牺牲证据链

画布不是摘要的美化版，而是带指针的索引：每个节点都挂着 node_id，每个 node_id 都能在 offload.jsonl 里换到 result_ref，每个 result_ref 都指向一份未被动过的原文。 压缩发生在「表示层」（日志 → 符号），不发生在「证据层」（refs 原文原样保留）。 这与「摘要即终点」的方案有本质区别：后者的错误不可撤销，前者的错误可以回滚到原文重新判断。 换句话说，token 省在表示上，责任不省在证据上。

R = T画布T日志 ， T注入 ≤ β · T上下文 ， β = 0.2（mmdMaxTokenRatio 默认值）
README 自报：接入后 WideSearch 的 token 从 221.31M 降到 85.64M，降幅 61.38% 自报·未复现——即上式 R 的一次经验取值；β=0.2 则是代码里写死的注入预算上界。

批判评估：三条隐性代价。其一，阈值与超时都是经验常数 （4 条 / 300 秒 / 120 秒重试），README 与源码均未给出消融依据，不同任务节奏下是否最优未知。 其二，wait 态依赖重试的最终一致性：若 LLM 持续解析失败，条目会反复排队， 画布与真实日志之间出现窗口期的偏差——注入模板里「进程可能有延迟，仅供参考」这句免责， 某种程度上就是对这种偏差的官方承认。其三，画布自身也要对抗噪声：源码里专门过滤了 HEARTBEAT.md 心跳类条目（isHeartbeatEntry），说明符号层同样会被自己的高频日志污染， 分层并没有免除清洗工作，只是把清洗从「上下文预算」挪到了「画布生成」阶段。

CHAPTER 04

记忆即负载：ACL 与 per-agent loadout

前两章讲的是「怎么存、怎么压」，本章讲「给谁用」。report §4.1 把这套机制概括为 记忆即负载（loadout）：记忆资产不是全局广播的，而是按可见性分级、按 Agent 绑定装配的。

四级可见性、双层角色与一等资产

  • 四级可见性 + ACL：私有（private）/ 团队（team）/ 受限（restricted）/ Agent（agent） 四级，配合 ACL 裁决谁能看到什么；同一份记忆对不同主体呈现不同的可见性。
  • 双层角色：Global System Admin（全局系统管理员）负责系统级治理， Team-level roles（团队级角色）负责团队内的日常管理——治理权被切在两个尺度上， 避免所有权限都涌向单一全局管理员。
  • per-agent loadout：按 Agent 绑定不同资产。这一步把「注入什么」的决策 从 prompt 层前移到了资产层——每个 Agent 出厂自带一份装备清单，而不是靠 system prompt 里堆说明。
  • Skill 是一等资产：带版本、资源、触发边界、校验规则， 与记忆资产同级管理；知识侧的 LLM-Wiki 与 Code-Graph 则是工具化查询而非整体注入—— 「不让 Agent 每次先读完整文件清单再干活」。

设计 rationale：为什么叫「负载」而不是「上下文」

架构洞察：loadout 这个军事/游戏隐喻选得很准——装备是有限格位的， 装了 A 就装不下 B，且不同角色带不同配置。把记忆类比为负载，等于承认三件事： ① 注入预算是一种稀缺资源，必须分配而非填满；② 分配的单位是「资产」（带 ACL、带版本）， 而不是散落的文本片段；③ 装配发生在运行前（按 Agent 绑定），而不是每轮对话中临时拼装。 对比纯 RAG「查询时再捞一批」的被动模式，loadout 是主动的预算前置分配。

设计意图很清楚：抽取成本被摊薄到多轮、被空闲窗口错峰、被单次条数上限封顶、被召回超时兜底—— 「后台持续抽取」被改造成一条可节流、可关断的管线，而不是无底洞。
批判评估

自报基准的复现风险与后台抽取的真实成本

report §4.1 把「依赖 LLM 后台持续抽取（token 成本、延迟）」明确列为风险项。这笔账有两面： 上表的旋钮说明项目知道成本存在并做了节流，但节流的另一面是记忆的新鲜度延迟—— 空闲 600 秒才抽、每 50 条才更新画像，意味着「刚说完的事」在画像层是缺席的。
基准数字方面：PersonaMem 准确率 48%→76%（相对 +59%）、 WideSearch 通过率 33%→50%（相对 +51.52%）、token 221.31M→85.64M（−61.38%）、 SWE-bench token −33.09%、AA-LCR token −30.98%—— 自报·未复现，全部来自项目 README，本读书会未做复现实验； 其测试设定（连续长程 session、SWE-bench 每 session 50 个任务）同样是自述 自报·未复现。读这套数字的正确姿势是「方向性参考」： 它证明了卸载与分层能带来数量级的 token 节省，但不能直接换算成你场景里的收益。

替代方案对比：另一条路线是 rolling-memory 式的零后台 LLM—— 不做任何抽取，纯词法检索 + 原文档案，检索约 30ms自报·未复现、零抽取 token。 代价是它对自然语言的零重叠查询（昵称、省略主语）偏弱，而那恰是社区陪伴场景的主战场。 两条路线不是谁淘汰谁：抽取路线买的是「结构化先验」，零 LLM 路线买的是「零成本与零幻觉」， OIA 的合理姿态是先建零成本基线，再在其上叠加可节流的蒸馏层。

移植落点与边界：OIA 拿什么、不拿什么

走读的终点是决策。code-level-notes §2 已经把「可直接搬运」的内容逐文件列了清单， 本章把它放进取舍框架里看：哪些是结构（照搬）、哪些是提示词（改写）、哪些是服务（不接）。

移植路线拿什么代价结论
整套照搬 抽取 + 去重 + 画布 + schema + 治理面板全套 绑定其宿主 hook 与目录约定，改造成本后置爆发 不取

三处具体的「改写点」

  1. 抽取提示词：情境切分 + 三类记忆（persona / episodic / instruction）+ priority 分档 + 负面清单的骨架直接沿用，但 OIA 需要加一条「旧措辞保留为 superseded 历史」—— 这是 MemoraX/续忆一系对「取代留痕」的要求，本项目只做覆盖与合并。
  2. 去重动作集：store / skip / update / merge 四动作与 target_ids 多对多合并是现成骨架；同样要补留痕语义，否则 merge 会抹掉演化过程。
  3. 画布组件：node_id/result_ref/refs 三层结构、阈值 4、wait 重试、注入模板 可以结构照搬并翻译成 OIA 文案；DSH 侧的对应物是 compaction 后端 + tool-result pruner 的配合。
深度洞察

白盒不是文档，是可执行的调试路径

很多系统也写「可观测性文档」，但只告诉你去哪看日志；这个项目的白盒是 数据结构本身保证的——因为层间以溯源字段（scene_name、source_message_ids、node_id、result_ref） 硬连接，「打开目录沿链走」才成为可能。给 OIA 的启示：治理面板的「召回透明页」不要做成事后埋点， 而要在写入时就把链路字段存全；可追溯性是 schema 的属性，不是 UI 的功能。

边界：哪些东西不该拿

  • 云向量库后端（TCVDB）：本地 SQLite + sqlite-vec 已够用，与 OIA 本地优先相悖的部分不接。
  • 宿主侵入性：README 的 Quick Start 需要注册 contextEngine 槽位， 还要跑一次 openclaw-after-tool-call-messages.patch.sh 给宿主打补丁， 才能让 after-tool-call 消息被正确卸载与恢复。批判评估： 这说明它的短期压缩不是零侵入的插件能力，而是对宿主消息流的钩挂—— 移植到 DSH 时必须先确认等价 hook 是否存在，否则整条画布管线落不了地。
  • 尚未完成的部分：Roadmap 里未勾选的三项——跨 Agent/框架/设备的便携迁移、 自动生成 Skill、可视化调试与记忆可观测面板——是项目自己承认的边界， 不应当作已有能力引用。

跨文连接：把本篇放回六篇系列：本篇提供结构范式（分层 + 画布 + 白盒）， rolling-memory 提供零成本检索基线（自信息权重、原文档案）， MemoraX 提供写入策略（意图式保存 + 取代留痕）—— OIA 的 @omni/memory-distiller、@omni/memory-canvas 与治理面板 正好是这三者的汇合处。读单篇的意义在于知道每个零件从哪来、为什么这么设计。

② 冲突检测动作集：store / skip / update / merge 与 target_ids 多对多

去重不是「相似就丢」，而是一个四动作决策问题：store 视为新信息新增、 skip 忽略无增量、update 以新记忆覆盖旧记忆（可保留旧记忆中仍正确的细节）、 merge 把互补且不矛盾的多条合并成一条。两个设计尤其精彩： target_ids 是数组，一条新记忆可以同时替换候选池中的多条旧记忆（多对多合并）， 且允许跨 type 合并（一条 episodic 事件与一条 persona 属性可以合成同一事实）； merged_timestamps 取所有相关时间戳的并集，保证合并后事件的完整时间线不丢。 批量模式统一候选池 + 每条新记忆的相关候选 ID，一次调用全局去重，省轮次。

延伸问题与研究方向

延伸问题 Q1

语义金字塔各层的 token 预算，如何按查询类型联合优化？

理论分析：把问题形式化为一个受预算约束的选择问题。 设层 ℓ ∈ {L0, L1, L2, L3}，每层的注入成本为 cℓ、对查询类型 q 的检索价值为 wℓ(q)，注入指示变量为 xℓ ∈ {0,1}，则

maxx U(q) = Σℓ wℓ(q) · vℓ − λ · Σℓ cℓ · xℓ ， s.t. Σℓ cℓ · xℓ ≤ B

其中第一项是注入后的期望效用，第二项是注入成本（λ 为成本敏感度），B 为上下文预算。 同时，未注入的层并非零损失——它们以「需要下钻时才付读放大」的形式留存， 总代价可写成信息损失与读放大的加权：

L(x) = Σℓ (1 − xℓ) · H( Eℓ | Sℓ ) ＋ μ · Σℓ (1 − xℓ) · rℓ(q)

这里 H(Eℓ | Sℓ) 是该层证据相对其上层结构的条件熵（抽象损失）， rℓ(q) 是查询类型 q 触发该层下钻的预期次数（读放大）。 本项目的 β=0.2（画布注入上限）、maxResults=5、maxCharsPerMemory/maxTotalRecallChars=0（默认不设防） 实际上是在这条曲线上取了一个固定点——而非按查询类型自适应： 「查偏好」与「查日期」共用同一套预算，这正是可优化的空隙。

研究方向：① 查询类型感知的预算分配： 先用轻量分类器（或利用抽取阶段已有的 type 字段）判定 q 的类型，再按 wℓ(q) 的排序动态装填 loadout——偏好型查询多给 L3/L2，事实型查询直下 L1/L0， 进行中任务给画布留足 β；② 下钻代价的在线估计： 用 rℓ(q) 的历史观测（node_id 下钻成功率、result_ref 打开次数） 反馈校准 λ 与 μ，把「白盒可下钻」从承诺变成带延迟指标的服务等级； ③ 基准设计：现有自报数字 自报·未复现只报告了端到端收益，缺少「哪层贡献了多少」的消融—— 按查询类型分桶、逐层开关的消融实验，是检验「分层确实必要」而非「分层恰好没坏」的关键证据。

延伸问题 Q2

「wait」态与固定阈值 4，能否换成自适应触发？

理论分析：固定阈值把画布刷新的延迟与压缩率锁死在一组经验常数上 （4 条 / 300 秒 / 120 秒重试）。若把每次 L2 的收益记为节省的 token、成本记为一次 LLM 调用， 则最优触发点满足「边际节省 = 边际调用成本」，而这个等式随任务节奏（工具调用密度）与模型价格实时漂移—— 常数解只能在某个工作点附近最优。

研究方向：以 offload.jsonl 的到达过程为输入（点过程或滑窗密度）， 在线估计下一次画布生成的期望净收益；wait 态则可引入失败率反馈—— 连续失败时指数退避而非固定 120 秒，并把「画布与原文的偏差时长」纳入可观测指标， 让「进程可能有延迟」这句免责变成可测量、可告警的量。
