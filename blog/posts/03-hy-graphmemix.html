CHAPTER 01

双过程节律：快检索 + 慢整理

Hy-Memory 的 README 快照开宗明义：这是一个 production-grade dual-system cognitive memory（生产级双过程认知记忆引擎），三场景（chat / working / coding）各有一条管线。但真正决定它「像不像认知系统」的，不是场景路由，而是读写与整理在时间轴上被刻意错开这件事。

System 1：每一轮都要在场的快路径

lite 与 pro 承担 System 1。add() / search() 在对话轮内同步完成：lite 是纯向量读写——README 快照写明它 raw-only embedding writes and searches, no LLM calls，连 scene 和 layers 都被忽略；pro 在其上加 LLM 抽取 + 对账（reconcile），图库可选（MEMORY_ENABLE_GRAPH，默认关）。这条路径的 KPI 只有一个：不拖慢这一轮对话。

System 2：被显式叫醒的慢路径

ultra 模式多出的是 schema 归纳与跨域清扫（cross-domain sweeper），它们由 client.evolve(user_id=...) 触发，不是每轮自动跑；图库在 ultra 下常开（Kuzu 默认 / Neo4j 可选）。README 快照的新闻栏还提到 nightly evolve（夜间演化）——即「定时 + 显式调用」两种唤醒方式并存。

模式做什么图库LLM 调用适用
lite仅原文嵌入读写；忽略 scene / layers无零纯向量 RAG、快速摄入
prolite + LLM 抽取 + 对账可选（默认关）每轮抽取/对账标准负载
ultrapro + System 2 schema 归纳 + 跨域清扫（evolve() 触发）常开写路径 + 演化期集中完整认知架构

为什么整理必须与读写解耦——延迟预算

把 schema 归纳塞进 add() 是最直觉的方案，也是最贵的：归纳要遍历图、要比对冲突、要跑一次长 prompt 的 LLM 调用，这些全都会落在用户正在等的那一轮上。evolve() 把它们整体挪出 P95 延迟路径，代价则是——两次 evolve 之间，记忆保持「未归纳」状态：L6 心智模型可能是旧的，跨域冲突可能还挂着。这是一个明确的换算：用「结构的新鲜度」换「对话的响应性」。

替代方案盘点：① 每轮都整理——延迟爆炸，等于放弃 System 1；② 纯后台定时线程——不可控，且与写入竞争（README 快照显示它选了 nightly evolve + 显式 evolve() 的混合，两条都留）；③ 全量离线批摘要——这正是 GraphMemix 摘要里点名的第一坑（见第 4 章）。Hy-Memory 的选择是只在被问到时才整理，整理本身也带触发条件，而不是无条件重算。

洞察

双过程不是两个模型，是两笔预算

System 1 与 System 2 的差别不在「聪明程度」，而在被允许花多少时间：前者花在每一轮的延迟预算里（lite 甚至把 LLM 预算设为 0），后者花在没人等的离线预算里。任何把慢活塞进同步路径的系统，最后都会被迫把慢活砍掉——解耦是让慢活活下来的前提，而不是让它跑得更快。

出处：docs/sources/hy-memory.md（README 快照 · 三场景 / Modes 表 / evolve() API）

跨文连接（第 2 篇）：rolling-memory 的零成本词法层与这里的 lite 档是同一个直觉——检索/写入的底线路径必须不依赖 LLM，模型只做增量增值。区别在于 rolling 把「零成本」做进了权重公式，Hy-Memory 把它做成了运行档位。

CHAPTER 02

八层结构与 L7 前瞻意图

chat 场景的记忆是一条 L0→L7 的抽象梯子：从原始对话逐层蒸馏到事实、摘要、心智模型，最顶层放的是「将来要做什么」——前瞻性记忆（prospective memory）。README 快照的层级表如下：

层名字内容
L0BASIC_INFO基本信息
L1RAW原始对话（append-only）
L2FACT原子事实（版本化、不可变记录）
L3SUMMARY会话摘要
L4IDENTITY保留（Reserved）
L5KNOWLEDGE保留（Reserved）
L6SCHEMA心智模型（抽象叙事模板，图层）
L7INTENTION前瞻意图（带过期；过期后降级为普通事实）

L7 字段与三个消费点

意图的字段定义在 hy_memory/agent/intention_detector.py 的提示词里（本地源码存档，前 80 行实读）：content、trigger_type（time_based / event_based）、trigger_condition、trigger_time（ISO 时间，非时间型为 null）、trigger_event_pattern、priority（high/medium/low）、expiry（ISO 过期时间，可为 null）、is_proactive_care（关怀型）。提示词还单列了第三类触发——关怀型：「考试快到了好紧张」不是明确计划，但系统应在考后关心结果。

该模块的 docstring 列出三个消费点：① Write Path（System 1）轻量检测、快速入队；② Read Path 检查当前对话是否触发已有意图；③ System 2 深度分析意图细节、设置触发条件——即 L7 同样吃双过程节律：入队要快，条件精化可以慢。

意图存活 ⟺ expiry = null ∨ now < expiry； 过期 ⟹ 降级为 L2 普通事实（保留 content，撤销触发权）
过期不是删除——这条生命周期与第 4 篇的「记忆养护/归档」是同一治理直觉
洞察

「降级」比「删除」和「永久保留」都好

过期意图有两种朴素处理：删掉（丢内容）或永远留着（未来某天误触发，拿三个月前的承诺骚扰用户）。降级为普通事实是第三条路——它作为「事实」仍然可被检索到（用户问「我上次说要干嘛」时能答），但不再拥有主动触发权。触发权被显式回收，这正是主动性系统最需要的刹车。

出处：hy-memory README 快照 L7 行（"with an expiry; demoted to ordinary facts once expired"）

一处源码与 README 的命名漂移（如实记录）

intention_detector.py 的 docstring 写着「L6 层: 记住"将来要做什么"」，而 README 快照的层级表把 L6 定为 SCHEMA、L7 定为 INTENTION。两份本地存档对不上——本页以 README 快照的 L0–L7 表为层级名的准绳，以源码为准的只有字段与触发类型。这类漂移不臆断、不调和，原样记录，是反幻觉写作的底线。

为什么/代价/替代：把意图放进记忆系统而不是另起一个 reminder 模块，好处是意图能被上下文触发（「下次聊到旅行」必须靠对话内容判断，日历做不到）；代价是误检会打扰，所以 schema 里同时给了 priority 和 expiry 两道闸。替代方案是纯日程 crontab——零误检、零语义，但事件型触发根本无法表达。Hy-Memory 的答案是让三种触发（时间/事件/关怀）共用同一张表、同一套过期语义。

跨文连接（第 5 篇 · Coco 主动性）：is_proactive_care 正是主动性论文那一族问题的数据侧落点——第 5 篇讨论「何时出声」的策略，这里的关怀型意图提供了「出声的理由」；两者合起来才是完整的干预链：检测到该关心的信号 → 策略器决定现在说还是沉默 → 表达层决定怎么说。OIA 侧对应 InterventionPolicy 的 SEEK_FEEDBACK / 关怀通道（见 code-level-notes §3.2）。

CHAPTER 03

diff-chain：装饰器不是检索器

chain_store.py（924 行，本地存档实读前 120 行）的 docstring 自称设计文档，第一句话就划清了边界——「它是装饰器, 不是检索器」：

向量层(hy_mem / 任何 RAG)负责「给哪几条 fact」—— top-k、阈值、排序全归它。
本模块只负责「每条 fact 后面跟什么」: 把那条 fact 讲的那处代码, 在这条分支上的全部改动版本(每版的用户原话 + 每版的真实 diff)按顺序挂在它下面。
不做相似度、不做 top-k、不选版本、不猜哪版是最终答案。判定权交给指令本身。
—— hy_memory/coding/chain_store.py docstring（源码原文，本地存档）

为什么必须存 diff：200 字预算与「读不回来的版本」

事实抽取的 prompt 明文要求砍代码（同 docstring 引用 extractor.py）：「A record that omits the branch but quotes 30 lines of diff is a bad trade.」「EXACT COORDINATES, NOT PASTED CODE」，硬上限约 200 汉字。这个取舍在通用场景下是对的——200 字里 feat/x 这一个 token 的价值远超 30 行 diff，而代码「可以回去读」。

但它假定的前提有个洞：被撤掉那版的代码读不回来。它不在工作树、不在 HEAD，只可能在某次中间提交里；对话里 s.replace 式的合成编辑甚至从未有过 commit。于是出现一个信息论死角——摘要机制系统性丢弃的，恰好是最不可再生的那一类信息。

diff-chain 的回答是不跟那 200 字抢：抽取 prompt 一个字不改，本模块零 LLM 地把每版真实 patch 存下来。补的不是「抽取质量」，是 LLM 摘要必然丢掉的那一类信息。

两表结构、隔离键与三级降级

表：thread(id, owner, branch, file, symbol, lo, hi, n_rounds, updated_at) + round(id, thread_id, seq, said, patch, adds, created_at)（另有 repo_symbol 全仓 AST 索引，只用于「指令点名的函数在哪个文件」，不参与分链）。

隔离键：owner = "<user_id>|<workspace_id>" 必须进键——没有它时用户 A 的 feat/q4 和 B 的 feat/q4 会并成同一条链，A 能读到 B 的 diff。空串 = 未指定且只匹配空串（不是公共池），单用户老库行为不变。这是安全边界，不是优化。

三级 thread 键降级（都在 owner 之内）：① hunk header 带函数名 → (owner, branch, file, symbol, 行区间)；② 只有上下文无函数名 → (owner, branch, file, 行区间聚类，LINE_MERGE = 20 行)；③ 裸 hunk 只有行号 → (owner, branch, file)。② 不直接降到文件粒度，否则同一文件所有改动挤成一条十几版的长链，分不清哪版对应哪件事。也不用 repo_symbol 按行号反查补 ②——patch 里的行号是改后的、索引是改前建的，会系统性偏一个符号；hunk header 才是对的。

block_chars ≤ MAX_BLOCK_CHARS = 14000； 每版 code ≤ 6 行 ∪ 480 字；每版原话 ≤ 800 字； 每 fact 挂链 ≤ TOPN_THREADS = 3，挂链 fact ≤ TOPN_FACTS = 1
全部为 chain_store.py 源码默认值（env 可调），非估算——见代码附录块 ③

失败闸门：后果不对称论证

对话里的合成编辑（open → s.replace → 写回）原先只要正则抓到 path/old/new 三段就当「改动发生了」，不看有没有成功。两类误判：agent 只是提议改法（还在问「要我执行吗」），用户回「这个方案不对，别改」→ 照样存；编辑失败（AssertionError: old not in s）→ 失败的那版也进链。

源码注释给出的否决理由是后果不对称：链是「哪一版赢了」的唯一依据，掺进一个没生效的版本，agent 后续可能照着一个从未存在的代码写。这与该函数自己的原则（「抽错比抽不到更坏」的反面——此处抽错代价更高）一致：宁可少一版，不可错一版。

洞察

「装饰器」是接口纪律，不是修辞

把编辑史做成独立检索器，就要回答「谁排前面」——于是要打分、要阈值、要跟向量层抢 top-k，两套排序互相不知道对方存在。声明自己是装饰器后，排序权唯一归向量层，本模块只保证「挂上来的东西全且真」。工程上这叫单一事实源；认知上这叫把「相关性判断」与「证据完备性」拆成两个可以分别验证的组件。

出处：hy_memory/coding/chain_store.py docstring「它是装饰器, 不是检索器」（本地存档）

代价与替代：存储随版本数线性增长；注入预算被挤占（所以才有 SHOW_ALL=8、TOPN_THREADS=3、TOPN_FACTS=1 三层截断——源码注释明说「宁可少挂一条链也不把原话压短」，因为原话才是这个机制的核心信息）。替代方案：① 让抽取 prompt 带代码——源码明说这是 bad trade，且 30 行 diff 会挤掉 branch；② 依赖 git 历史——对话内合成编辑没有 commit，且需要 MEMORY_CODING_CHAIN_REPO_ROOT 配置；③ 让 LLM 改写 diff——有损且可能幻觉出从未存在的代码。零 LLM 的原样存 diff 是三者中唯一不引入新错误模式的。

跨文连接（第 1 篇）：TencentDB 的抽取提示词同样强调「独立完整、宁缺毋滥」，与这里的 200 字坐标预算是同一种写入端克制；两者共同的推论是——摘要端越克制，越需要一个零 LLM 的原始证据层兜底（第 1 篇是原文档案，本篇是版本 diff）。

CHAPTER 04

GraphMemix：召回是预算化证据选择

2026-11-21 · 全文精读修订

前三章讲记忆怎么被写好、长好；GraphMemix（arXiv 2608.26983v1）讲另一半——被问到时，怎么从记忆里挑出一个「证据包」。本章已升级为全文级（本地全文 HTML + 配套代码实读，笔记见 docs/sources/papers/notes/04-graphmemix.md）；先照录摘要骨架，再逐条补上摘要里没有的增量：

"Organizing long-term memory for multimodal agents remains challenging because existing methods either suffer from expensive question-agnostic offline summaries or naive embedding similarity matching that introduces incomplete and redundant context. To address this issue, we propose GraphMemix, a combinatorial-optimization graph memory framework that models memory organization as query-aware evidence-forest construction. Specifically, our method consists of three key components: (1) candidate graph construction, which expands multi-view seed memories through schema and semantic relations to obtain query-aware original context; (2) evidence utility and activation costs, which decouples direct memory support from anchor-conditioned relation verification to suppress redundant or conflicting information; and (3) forest optimization, which jointly selects a forest-format memory context under a maximum evidence budget and its reliable relational structure. By organizing memory into a query-relevant subgraph, the method avoids substantial lifecycle cost and recovers low-similarity complementary evidence. Experimental results across four long-term multimodal memory benchmarks demonstrate significant improvements with different foundation models and establish a new Pareto frontier between accuracy and lifecycle cost." —— papers-abstracts.md §4 摘要原文（已全文精读，此段仍作骨架照录）

三组件拆解

  1. 候选图构造（candidate graph construction）：从多视角种子记忆出发，沿 schema 关系与语义关系扩展，得到「查询感知的原始上下文」——注意扩展是围绕查询的，不是全库遍历。
  2. 证据效用与激活成本（evidence utility and activation costs）：把「直接记忆支持」与「锚点条件关系验证」解耦，用激活成本抑制冗余与冲突信息——相似不代表有用，两条互相矛盾的高分记忆会各自计费。
  3. 森林优化（forest optimization）：在最大证据预算下，联合选出森林格式的记忆上下文及其可靠关系结构。输出不是一串平铺的 Top-K，而是一片带边的子图。

它反对的两个坑

做法病灶GraphMemix 的对治
问题无关的离线摘要摘要时不知道将来问什么 → 按「平均重要性」压缩，问到时该留的没留；且摘要本身要花大量生命周期成本查询感知：围绕当前 q 组织子图，避免 substantial lifecycle cost（摘要原文）
朴素向量 Top-K相似度 ≠ 证据力：上下文不完整、冗余重复、互相冲突；低相似的互补证据被埋掉效用与激活成本解耦 + 森林优化抑制冗余冲突，恢复 low-similarity complementary evidence（摘要原文）

低相似互补证据为什么重要：用户用模糊描述找旧事时（「我之前是不是说过那个……」），最相关的那条记忆往往措辞与查询毫不相似——它描述的是同一事件的另一个侧面。纯余弦相似度对此无解；关系边（同锚点、同实体、同时间）提供了相似度之外的第二条通路。这正是「图」在这套方法里存在的理由，而不是装饰。全文的恢复率实验（自报）：在「候选图里确实有 gold」的合格问题上，GraphMemix 恢复了 40.08–68.48%，这些被找回的低排名记忆占全部保留 gold 对的 12.01–19.58%自报·未复现——注意分母是合格问题，不是端到端 recall。

洞察

召回的正确形式是带约束的组合优化

Top-K 的隐含假设是「分数可加、彼此独立」——于是取前 K 个即可。但证据进入同一注入窗口后会互相挤占、互相印证或互相矛盾，独立性假设崩塌。GraphMemix 把它改写成 max 效用 s.t. 约束 的组合问题：每条候选带效用与激活成本，选的是一个结构（森林），不是一段列表。这个形式化换来的直接收益，就是能明确回答「为什么这条相似度低却该进」——因为它补了一条没人覆盖的关系边。

出处：notes/04-graphmemix.md §3（式 1–13）· 论文 §3.2/§3.5

优化目标的真实形态：式(11) 与式(12)

摘要只说「under a maximum evidence budget」，全文给出的是三段式目标——节点效用 − 边激活成本 − 开链成本，预算体现为基数硬约束 |S| ≤ K（实验 K=10）：

(Sq★, Fq★) = argmaxS,F [ Σi∈S pi(q) − λ Σe∈F ce(q) − κ·m(S, F) ] s.t. S ⊆ Cq, |S| ≤ K, F ⊆ Eqtrust[S]
式(11)：m(S,F) 为森林连通分量数（每条分量 = 一条需独立解读的证据链）；λ=0.1，proposal 阶段 κprop=0.2、细化阶段 κ=0.12

关键化简（式 12）：边成本非负、删环不降目标 ⇒ 最优 F 可取为森林 ⇒ m(S,F) = |S| − |F|。定义结构增益 Be(q) = κ − λ·ce(q)，目标等价于：

Σi∈S ( pi(q) − κ ) + Σe∈F Be(q)
式(12)：自适应基数来自 κ，而不是逐节点罚项——孤立记忆必须「自证开得起一条独立链」（贡献 pi−κ）才保留；经正增益边并入已有分量则找回一份开链成本

为什么（设计 rationale）：若只做 Top-K，低效用但成对互补的证据会被各自计费地挤掉，而孤零零的高分证据霸占名额。κ 把「证据链的数量」变成显式价格：受保护的是可信的互补证据，被删的是低效用的孤立证据——这是「预算给谁」问题在目标函数层面的回答，而不是事后的多样性重排。

代价：κ、λ 是两个必须标定的旋钮（论文跨四基准冻结这组值）；κ 过大把成对证据也拆散，过小则分量数爆炸、reader 收到一堆互不相干的短链。

两阶段确定性求解：6 次 swap 就饱和

  1. 阶段一（固定基数 proposal）：top-K 节点效用初始化，每次评估一个「已选↔未选」的 1-swap，对每个提案节点集用 Kruskal 精确重算最大权森林，终止于确定性的 1-swap 局部最优。
  2. 阶段二（冻结 proposal 内的变基数精确解）：对正增益边跑 Kruskal 得 FS★，再枚举冻结提案的全部非空子集 2K−1 = 1023（K=10）取全局最优；平局先偏好更少记忆、再偏好更早的 proposal 排名。

实证（6,592 个评测问题的求解审计）自报·未复现：外层 1-swap 前几次被接受的交换就贡献了绝大部分均值目标改进，6 次之后变化可忽略——「有界 proposal 只需少量交换即可被修正，而每次交换都用精确 Kruskal 评估其最优诱导森林」。诚实边界：论文只声称「冻结 proposal 内精确」「每个被考虑节点集的森林精确」，没有给运行时间上界、近似比或收敛定理。

lifecycle cost 的真实定义：一次 digest + 一次答题的估计耗时

摘要里的「lifecycle cost」既不是 FLOPs 也不是 token 计数——全文 §4.3 的定义是：把全部记忆 digest 一遍 + 把全部问题各答一遍的估计 wall-clock。ATM-Bench（11,034 条记忆 + 1,044 题）上相对基线缩短 1.78×（vs A-MEM）/ 4.27×（vs VimRAG）/ 4.74×（vs LightMem）；另三基准估计 2.19 h / 2.71 h / 3.44 h 自报·未复现。诚实边界：这是估计耗时，硬件/端点/并发配置未在全文中找到；Pareto 前沿只相对「被比较的这几个方法」成立，不能外推到所有记忆系统。

自报结果与批判

论文自报：Qwen3-VL-8B 上四基准宏平均 49.80% → 61.55%（+11.75pp）、Gemma 4 12B 上 67.42%，两个 backbone 的 Judge Accuracy 全胜，并在准确率与生命周期成本之间建立了新的 Pareto 前沿 自报·未复现——本页已全文精读（含代码实读），但未复现任何数字、不引用论文任何图表，插图全部自绘。

批判一：组合优化的生命周期成本。摘要批评离线摘要「expensive」，但森林优化本身也要在每次查询时跑候选扩展 + 两次 listwise 验证 + 结构搜索。若在线计算成本高于一次离线摘要摊销到每问的成本，Pareto 前沿只是把成本从「写时」挪到了「读时」。而且 lifecycle 的口径是「估计 wall-clock」且硬件未披露——同一套算法在不同并发/缓存下，1.78× 与 4.74× 都可能被环境放大或抹平。

批判二：查询感知的延迟代价。查询感知意味着组织结构在线计算，延迟预算直接进对话轮；对需要即时响应的 agent harness，必须回答「森林没建完时先给什么」——论文没有给出降级路径的描述（对照 Hy-Memory 的 lite 档：它给了）。

批判三：依赖 schema 质量与标定数据。候选扩展走「schema and semantic relations」，schema 由谁维护、错了怎么修，全文未涉及——这恰是 Hy-Memory System 2（schema 归纳 + 跨域清扫）负责的那一段，两篇工作在这里恰好首尾相接；再加上效用系数用过 dev fold 的 gold，「冻结参数、不碰答案」的洁癖程度需要读者自行打折。

批判

最锋利的替代方案：预算给「谁」比预算给「多少」更难

朴素替代不是不做预算，而是按分数截断（先排序再砍尾）——便宜且无感知成本，但对「低相似互补证据」必然系统性漏检。另一极端是全量注入再让模型自己筛：把选择成本转嫁给上下文窗口与注意力，实际上是最贵的方案。受控实验已给出参照：MMR/DPP/facility 这类通用多样性先验在冻结预算下零增益甚至负增益，说明「换个花哨的重排器」不是出路——中间路线（如本页第 7 章的统一预算目标函数）仍待检验。

跨文连接：① 第 4 篇 · 琥珀之心的召回链（关键词/向量/图谱三路粗排 → 证据补充 → 模型精排 → LLM 细选）是同一问题的流水线式解法——分级过滤逐层兑现预算，比一次组合优化更易实现与调试；② 第 2 篇 · rolling-memory 的 compBound = (1/e)² · lex · (1 − exp(−lex/total)) 结构补偿上界，则是「候选扩展必须带质量上界」的公式化版本——与森林优化的预算约束是同一个思想在词法域的投影；③ κ/λ 作为「链数/边」的影子价格，与本页第 7 章的 compaction 预算统一问题直接对接。OIA 的落点（report.html §4.5）：候选合并与预算化精排，与琥珀两级精排合并设计。

RL 把长 prompt 吃成了 3 段：基线 GPT-4o control 用的是带 retrieval plan、十几条 query 规范（「用关键词短语、不要与历史查询语义重复」……）的长 prompt；RL 后的 M3-Agent 只剩 system_prompt / instruction_prompt / last_round_prompt 三段极简文本，H=5 轮、二值动作 [Search] / [Answer]、top-2 检索、最后一轮强制作答。这是「prompt engineering 被 RL 替代」的直接证据——表 7 里同样用简单 prompt 的 control-32b-prompt 只有 20.7，RL 后 30.7 自报·未复现。

为什么/代价/替代：手写规范是用人工替模型补策略，改一条规范要重新验证全链路；RL 直接把策略学进权重，prompt 只剩接口。代价是奖励与评测共用 GPT-4o 判官（0/1 奖励即判官输出），策略可能学会迎合判官措辞，而论文只报了判官与人工 96% 一致、未做敏感性分析。替代方案就是那条没走的路——纯 prompt 工程（已被表 7 的 20.7 vs 30.7 否定）或规则状态机（零训练成本，但空结果、换角度重查这类策略学不出来）。

「实体中心」的实现真相：等价类 + 并查集，不是边

  • 等价关系以一等公民语义节点保存：模型必须按 Equivalence: <face_x>, <voice_y> 格式输出跨模态等价行（禁用代词与编造名字，把指代消解降级为格式约束）；读图前 refresh_equivalences() 用并查集（按秩合并 + 路径压缩）把同一人的 face/voice 合成 character_i，fix_collisions 保证每个 voice 最多映射到一个 face。
  • 论文表 3 的 weight 属性在代码里不存在：Node 只有 id / type / embeddings / metadata，权重实际落在边上——reinforce_node / weaken_node 对所有相连边 ±1，且 add_edge 禁止同类型文本节点互连（实际边 = text↔img、text↔voice）。schema 表述与实现存在落差。
  • 投票发生在写入路径：语义记忆的实体集合若是某已有语义节点实体的子集，按余弦相似度投票——>0.85 强化（边权 +1）、<0 削弱（−1）、否则新建节点；冲突消解则推迟到读取时（fix_collisions 等）。
洞察

「实体中心」解决的是身份漂移，不是存得更多

人脸/声纹以原始特征存节点（每节点最多 10 个脸 embedding、20 个声 embedding），模型只被允许用 <face_i> 指代——把指代消解从生成任务降级为格式约束，再用并查集在读取时统一成 character_i。三层（持久锚点 / 符号化中间层 / 等价类）针对的都是「同一实体跨模态、跨时间的身份漂移」。迁移到 OIA 的屏幕/文档场景时机制可复用、锚点必须换：face/voice → 文件路径、URL、人名、工具名；而冲突消解放在读取路径（投票/阈值）、写入路径保持 append-only，这条取舍与 Hy-Memory 的 L2「版本化不可变」是同一味道。

出处：notes/06-m3-agent.md §3.1/§7.1（论文表 3 vs videograph.py 实读）

因果截断：这是评测机制，不是记忆机制

robot 集每条 QA 带提问时刻 timestamp 与其对应 before_clip；control 检索前先 truncate_memory_by_clip(before_clip)，只允许检索提问之前形成的记忆（清空 nodes/edges/文本索引/事件序列）；web 集问题时间戳全在视频末尾，故无截断。为什么必须有它：没有截断，agent 可以用未来信息回答过去的问题——记忆系统越强，这种作弊越隐蔽，多模态长视频尤其如此（视频后半段直接写着答案）。这让 benchmark 从「视频问答集」变成「带因果性的 agent 输入流」：视频=感知流，QA=在指定时刻发出的指令。代价是每题都得标提问时刻（robot 标了、web 没标，web 因此退化为全史问答）；替代方案是「只给全片、靠提示词承诺不用未来」——不可验证，等于没有。

箭头函数/对象方法等写法 git 默认 hunk header 认不出函数名, 会落到 ②。
② 用行区间聚类而不是直接降到文件粒度 —— 否则同一文件的
所有改动会挤成一条十几版的长链, 分不清哪版对应哪件事。

**不用** repo_symbol 按行号反查符号来补 ②: 它会系统性偏一个符号,
因为 patch 里的行号是改后的、而索引是改前建的。hunk header 才是对的。

⑤ M3-Agent 语义记忆的边权投票规则

实体集合是已有节点实体的子集时按余弦相似度投票：>0.85 强化、<0 削弱、否则新建节点。这就是论文所说 weight-based voting 的实现——注意 reinforce_node/weaken_node 作用于所有相连边（±1，边权 ≤0 即删边），Node 自身没有 weight 字段。

        # semantic memories can be used to update the existing text nodes, or create new text nodes
        elif type == 'semantic':
            for memory in memories:
                entities = parse_video_caption(video_graph, memory['contents'][0])
                if len(entities) == 0:
                    insert_memory(video_graph, memory, type)
                    continue

                # update the existing text node for each memory, if needed
                positive_threshold = 0.85
                negative_threshold = 0

                # get all (possible) related nodes
                node_id = entities[0][1]
                related_nodes = video_graph.get_connected_nodes(node_id, type=['semantic'])

                # if there is a node with similarity > positive_threshold, then update the edge weight by +1
                # if there is a node with similarity < negative_threshold, then update the edge weight by -1
                create_new_node = True

                for node_id in related_nodes:
                    # related nodes to be updated should satisfy two condtions:
                    # 1. the caption entities are a subset of the existing node entities
                    # 2. the semantic similarity ... shows a positive correlation or a negative correlation
                    related_node_entities = parse_video_caption(video_graph, video_graph.nodes[node_id].metadata['contents'][0])
                    embedding = video_graph.nodes[node_id].embeddings[0]
                    if all(entity in related_node_entities for entity in entities):
                        similarity = np.dot(memory['embeddings'][0], embedding) / (np.linalg.norm(memory['embeddings'][0]) * np.linalg.norm(embedding))
                        if similarity > positive_threshold:
                            video_graph.reinforce_node(node_id)      # 边权 +1
                            create_new_node = False
                        elif similarity < negative_threshold:
                            video_graph.weaken_node(node_id)         # 边权 -1，<=0 即删边
                            create_new_node = False

                if create_new_node:
                    insert_memory(video_graph, memory, type)

def attach_chain(fact, query, budget):
    # 1) 只挂「这条 fact 讲的那处代码」的链 —— 排序权仍归向量层
    threads = chain_store.threads_of(
        owner=f"{user_id}|{workspace_id}",   # 隔离键必须进键
        file=fact.coordinate.file, symbol=fact.coordinate.symbol,
    )
    threads = rank_by_token_overlap(threads, query)[:TOPN_THREADS]  # 默认 3

    # 2) 每版只带「用户原话 + 真实 diff」，seq 用调用计数，不做覆盖推断
    rounds = [r for r in chain_store.rounds_of(t) for t in threads]
    rounds = [r for r in rounds if r.seq <= SHOW_ALL]            # 默认 8

    block = render_block(rounds, max_chars=MAX_BLOCK_CHARS)         # 默认 14000
    return clamp(block, budget)  # 失败闸门: 未执行/已失败的编辑不得入链
CHAPTER 07 · OPEN QUESTION

延伸问题：两个预算，一个窗口

本页横跨的两套机制——GraphMemix 的证据预算与 harness 侧的 compaction token 预算——都在争夺同一个物理对象：注入窗口。它们应该被统一吗？

研究问题

证据森林的证据预算与 harness compaction 的 token 预算，能否统一为同一目标函数？

理论分析：把注入窗口总容量记为 Bwindow，记忆证据占用 Bevi，compaction 保留的历史摘要占用 Bcap，则当前两套系统各自求解 max Uevi s.t. Bevi ≤ Bevicap 与 max Ucap s.t. Bcap ≤ Bcapcap，而真正的约束只有一个：Bevi + Bcap ≤ Bwindow。拉格朗日视角下，两套预算的边际价值应当在同一个乘子 λ 上相等——否则把一格 token 从 compaction 挪给证据（或反之）总能提高总效用，说明解不是最优的。统一目标函数的候选形式：

maxF, C [ Uevi(F) + Ucap(C) ] s.t. Σe∈F cost(e) + Σh∈C len(h) ≤ Bwindow

其中 F 为证据森林、C 为 compaction 保留的摘要片段。难点在效用不可比：Uevi（答对当前问题的边际贡献）与 Ucap（防止未来轮次遗忘的期权价值）一个偏即时、一个偏跨时——后者是跨期的，只有引入时间贴现或遗忘风险模型才能同尺度相加。rolling-memory 的结构补偿上界 compBound = (1/e)²·lex·(1−exp(−lex/total)) 提供了一种「给扩展设上界」的先例，但它是词法域的启发式，不是对偶解。

研究方向：① 可测性先行——在 OIA 召回透明页（琥珀式 stats 贯穿）上同时记录 Bevi / Bcap 的实际占用与各自带来的答题贡献（逐题 JSONL 复算，借第 2 篇的评测纪律），先验证「边际不等」是否真的发生；② 预算交易市场——给 compaction 与证据各设一个影子价格 λ，超预算时按 λ 竞价而非按固定切分；③ 对照实验——固定切分 vs 静态比例 vs 联合优化三臂，观察低相似互补证据的召回率是否随 λ 的统一而提升；④ 降级路径——联合优化未收敛时回退到「证据优先的固定切分」，保证延迟预算不被优化本身吃掉（呼应第 1 章的解耦逻辑）。

洞察

预算的统一，本质是「谁有权决定挤掉谁」

只要两个预算由两个互不知情的组件分别执行，就一定存在「一方把窗口吃满、另一方的证据被静默丢弃」的暗角——而静默丢弃是最坏的失败模式，因为调用方看不到。统一目标函数的价值不在数学漂亮，而在让挤占变成显式交易：每次让渡都带价格、可记录、可复盘。这也是召回透明页与 harness compaction 日志应该共用一套账本的现实理由。
