第一章 · 四类记忆边界

MemoraX 的四类边界：按「谁的、多久有效」切记忆

MemoraX Code 的 README 没有给一个笼统的「记忆库」，而是把记忆切成四类，每类各自回答一个问题。边界不是分类学练习——它决定了这段记忆存在哪里、什么时候注入、什么时候失效。

记忆类型它回答的问题README 给的例子
Coding Memory（工程教训）哪些工程教训该带进下一个任务？已验证的修复、失败的尝试、设计理由、坑、回归检查
Repo Memory（仓库架构）智能体该知道这个仓库的什么？架构地图、模块归属、入口点、commit/PR/MR/issue 证据
Personal Memory（User Profile 沟通偏好）该怎么和你沟通协作？语言、语气、解释深度、结果格式
Procedure Memory（任务步骤）这类任务该怎么执行？可复用步骤、清单、前置条件、例外、验证闸门

作用域：为什么是 2×2，而不是四张清单

源码级笔记与 README 给出了作用域的硬证据：Personal 与 Procedure 全局于用户，存放在 $MEMORAX_CODE_HOME/personal-memory/（默认 ~/.memorax-code/personal-memory/）下——User Profile 用 user-profile/preferences.md，每个 Procedure 主题各占一个文件；README 明确「适用性可以提到某个仓库、工具或工作流，但仓库里不存在 personal-memory 层」，且已有的 .repo_memory 个人记忆文件会被忽略、不迁移。Coding 与 Repo 则跟随仓库或工作区。

为什么这样切：作用域决定注入时机与失效条件——用户级记忆跨会话、跨仓库永续，任务级记忆随仓库生命周期走。若混在一个池子里，作用域只能靠标签猜，猜错的代价是「换了个仓库还在念叨上个仓库的规矩」。代价是四类记忆要有四套路由与四套存储约定，写入侧多一次分类判断；README 让「怎么干活」进 Procedure、「怎么沟通呈现」进 Profile，本身就是一次路由提示。

替代方案：第 1 篇腾讯云记忆走的是另一条路——persona / episodic / instruction 三类打在同一批 l1_records 上，用 priority 区分轻重，作用域靠 session_key 表达。两种切法互补：MemoraX 按「谁的、多久有效」切边界，TencentDB 按「内容是什么」切类型；OIA 的 Vault 可以两者叠加——边界决定生命周期，类型决定抽取提示词。

洞察

意图式保存：把触发词从「记住」换成「长期有效」

README 的表述很克制：你说出一条打算长期生效的工作规则或偏好时，Agent 不等「记住」二字就存，并告诉你它存了什么；意图不明先问，一次性任务指令不改已存记忆。这把记忆写入的触发条件从显式命令移到了意图判定——用户的心智负担从「管理记忆」退回「正常提要求」。

出处：docs/sources/memorax-code.md「Four Clear Memory Boundaries」一节。

语义去重四动作与「取代留痕」

存之前先比对意义，README 给了四个动作：等价请求 → 不改；持久细化或冲突 → 更新匹配条目并移除被取代的措辞；作用域写错 → 纠正；只有整体过时 → 才删除。显式 forget 只删被点名的那条偏好 / 主题 / 章节 / 步骤，无关记忆不动。

跨文连接（第 1 篇）：这四个动作与腾讯云记忆的 store | skip | update | merge + target_ids 多对多合并、merged_timestamps 时间线并集是同一族设计；docs/code-level-notes.md §2.2 明说这就是 OIA「意图式保存 + 语义去重 + 取代留痕」的现成提示词骨架。

批判与代价：三者对「被取代的旧值」态度不同——MemoraX 是移除被取代的措辞（库里不留旧话），TencentDB 是 merge 进时间线（merged_timestamps 并集），续忆是小字留存（第 3 章）。OIA 要的「取代留痕」其实兼采两家：学 MemoraX 的意图判定与写前比对，但把 superseded 旧措辞保留为历史——否则「用户改过口」这件事在库里是不可审计的。

节奏注入：1 / 6 / 11 之后每 5 轮

源码级笔记记录的注入节奏：User Profile 在首个可用轮次注入；Procedure 默认在第 1、6、11 轮提醒，之后每 5 轮一次。compaction 之后还有一条恢复规则：一次被记录的 compaction 在原生数据库里得到验证后，下一个非空、注册过的 prompt 恢复 Profile 与个人提醒，Procedure 保持正常节奏；证据缺失就跳过恢复，同一条进行中的任务内不保证恢复。

Procedure 提醒轮次集合 T = {1, 6, 11} ∪ {11 + 5k ∣ k ≥ 1}

Profile 另计：首个可用轮次一次。

为什么（rationale）：compaction 是长上下文的有损压缩，用户级记忆一旦被压出窗口就等于「忘了」。节奏注入把「拉回来」变成一个定时器，不依赖任何检索命中——这是它与检索式召回最本质的区别。代价是固定节奏必然两头不讨好：不需要时也注入（空转），第 3 轮就需要却要等到第 6 轮（迟到）。替代方案是按需检索：琥珀之心的三路召回就是「拉」模式（第二章），MemoraX 是「推」模式。OIA 的取舍应是推拉结合——推保底（Profile/Procedure 永不漏），拉救急（任务相关记忆随叫随到）。compaction 本身是 DSH 的上下文机制，这条恢复规则也是与第 6 篇基座的连接点。

影响披露：答复尾注里的透明度

MemoraX 的「Visible memory impact」能力：当显式执行了 Coding Memory Search，或 Repo / Procedure / Profile 记忆实质引导了本轮任务时，它会在最终答复上打开一句简短的自然语言说明，覆盖 Codex、Claude Code、CodeBuddy CLI、WorkBuddy、DeepSeek Harness、OpenCode、Trae、Cursor、Qoder。配套的最小化原则同样值得注意：自动写回上传时会先去掉这条尾注，再把用户指令与最终答复送出去提取记忆。

洞察

三种「记忆影响了回答」的披露粒度

MemoraX 给一句尾注（有无）；琥珀之心把 stats 全程流转到召回透明页（分几段、每段多少候选）；Anima Brain 让分数随结果返回（每条为什么排这里）。可审计性是递增的：尾注只能回答「用没用」，stats 回答「怎么找的」，分数回答「凭什么选它」。

出处：memorax-code.md「Product Capabilities」；code-level-notes.md §4.1、§6。

代价：尾注只在「实质引导」时出现，而「什么算实质」是实现内部的判断——用户无法区分「没用到记忆」与「用了但不算实质」。替代方案是召回列表全量披露（琥珀的召回页把聊天原话、工具调用、每轮召回的记忆都摆出来），透明但噪声大；尾注安静但不可验证。这条权衡会一直跟到 OIA 的召回透明页设计。

第二章 · 琥珀之心

三路召回 + 人审状态机：把信任折叠进 48 小时

琥珀之心（Amber Heart）是为 AI 伴侣设计的长期记忆系统，按稳定程度分三层：固定记忆（人设与核心记忆，每次稳定注入）、短期记忆（书签、及时摘要、接力棒、最近 3 天日记）、长期记忆（结构化卡片 + 三路召回 + 两级精排 + 养护）。本章只拆两件事：召回链怎么保持透明，以及卡片入库前的那道人审闸门。

三路召回与五段管线

召回方式README 给它分的工
关键词召回明确的词、人名、事件名、健康词、专有名词——保准确
向量召回语义相近的记忆，解决「没说原词但意思接近」——保泛化
图谱召回沿人物、事件、主题和关系扩展相关记忆——保联想

源码级笔记对 memory_core/recall/recall.py 的实读给出了五段链：ThreeRouteSearch（三路粗排）→ replace_parents（父卡替换）→ add_rerank_evidence（证据补充）→ order_candidates（精排模型）→ select_candidates（LLM 细选），外加 TailContext（全列表模式）。三个 stats 诊断对象——retrieval_stats / ordering_stats / selection_stats——随管线一路流转，这就是「召回透明页」的数据源。

为什么（rationale）：单路向量的两个老问题——「明确的词找不到」和「联想串不起来」——分别被关键词路和图谱路兜住；README 自己也说它「不是单纯的向量库」。跨文连接：关键词路正是第 2 篇 rolling-memory 自信息权重的用武之地（code-level-notes 已把 OIA 的 recall-T0 定为「自信息权重 + 突发折叠」）。代价是每次召回要跑三路检索 + 合并去重 + 两次模型调用（精排与 LLM 细选），延迟与 API 成本都上去了；而且琥珀在「已知限制」里坦白：召回效果还没有公开的评测数字，评测工具和合成数据集在准备中——链路漂亮不等于链路有效。

待审核状态机与三重 CAS

长期记忆不是每句话都存：后台模型每晚扫描当天聊天，只提取承诺规则边界、偏好、健康事件与生活变化、深度讨论、你明确要求记住的事；卡片先进「待审核」页，你只需判断「这张写得对不对」——可修改、可拒绝，拒绝过的还能翻出来再看；没空处理的，48 小时后自动收录。

pending_memories 表上的状态集合（实读 docs/code-level-notes.md §4.2）：pending / structure_pending / structure_failed / approved / rejected / deleted，共六态；并发控制是三重 CAS——version（版本号）、review_key（防重复审批）、policy_revision（策略变更后重审）。policy_revision 不只用在审批上，recall.py 的召回路径里也有 self.store.check_revision(stats['policy_revision'])：策略改了，正在跑的召回也要对账。

48 小时：读 review_policy.py 才知道它不是定时器

memory_core/cards/review_policy.py 实读给出的关键事实：ApprovalSettings.delay_hours 默认 48，可用环境变量 MEMORY_AUTO_APPROVE_AFTER_HOURS 覆盖，且必须是正整数；真正参与调度的是它折算出的业务日：

delay_days = max(1, ⌈delay_hours / 24⌉)

源码写作 -(-delay_hours // 24)；注释说明：按营业日计，免得晚几分钟才抽出的草稿被整体推后一整天。

ready_before() / is_due() / scheduled_at() 把到期判定挂到每晚的批量任务上（README：每晚任务默认在你所在时区的凌晨 3 点多运行）；overview() 则为待审核页吐出 enabled / delay_hours / ready_count / manual_count / next_run_at / overdue / last_error_code 这组仪表。MANUAL_REVIEW = "manual_review_required" 的注释解释了它的语义：抽取之后设置或当天来源变了，自动收录就停下，人工在审核页保存草稿即清除。

洞察

48h 不是 48 小时的定时器，而是「两个业务日之后的那晚」

等待期被折算成业务日、再挂到既有的夜间批量作业上——为审核单开一个调度器的工程代价被省掉了。副作用是实际等待落在 48–72 小时的量级上，取决于抽取时刻与夜间任务时刻；而「超时自动收录」意味着没人看的卡也会入库，这是把查全兜底放在了查准之前。

出处：memory_core/cards/review_policy.py 全文实读（68 行）；amber-heart.md「长期记忆如何入库」。

人审漏斗 vs 全自动：信任的三种开法

全自动查全最高，但错卡直接进长期记忆、且会被每月的主题总结向上聚合——错误会「沉淀」成更难发现的长期理解；纯手动查准最高，但必然积压，ready_count 与 overdue 这两个字段就是为积压准备的仪表；48h 折中的代价很具体：按 README 的流程（聊天记录 → 每晚提取 → 待审核 → 确认或到期自动收录 → 入库），等待期内的卡片不在长期记忆库里，新事实在这两天内的查全是 0，换回的是「入库的卡大概率写对了」。

替代方案：按记忆类型分档等待。琥珀自己的归档规则已经这么干了——规则/约定/边界与高情感记忆约 1 年、里程碑至少 1 年、稳定事实与反思约半年、普通事件约 4 个月、极少数特殊记忆永不归档。同一套「按类型给参数」的思想搬到审核等待期，就是本页第六章的延伸问题。

诚实声明：琥珀 README 自报「1 GB 服务器实测：约 2000 张卡片、9000 多条历史消息的规模下，一晚补完 30 天积压的每晚任务」——自报·未复现，本系列未做独立复测；召回效果则连自报数字都还没有。

第三章 · 续忆

续忆：一个现成 DSH 记忆插件的用户主权接口

续忆是一个 DeepSeek Harness 插件，给 QQ 陪伴助手加长期记忆和日记本。它对本系列的价值有两层：形态上，它是第 6 篇 DSH 基座的现成范本；治理上，它把「纠正 / 抑制 / 时间限定」三件用户主权事做成了可点的按钮。

打包形态：package.json 里的 dsh 字段

实读 dsh-adapter/package.json："name": "dsh-xuyi-memory"、"type": "module"、"main": "./index.js"，exports 暴露 . / ./client / ./locale/*.json，license: "MIT"、engines.node >= 20，核心是那段 dsh 字段——bundle.patch 指向 ./cordis.patch.yml（补丁里 insert 一条 id: xuyi-memory），client.platform = "web"、immediately = true。files 清单同时说明了分工：index.js（Host 侧插件入口）/ client.js（Web 客户端面板）/ logic.js（业务，约 62 KB）/ rhythm.js（节奏）/ locale / images。

为什么（rationale）：记忆系统天然横跨两侧——存储、召回、夜间任务在 Host 侧，而「TA的记忆 / 日记 / 设置」面板必须在 Web 客户端；dsh.client 声明让宿主知道要装哪个入口、要不要立即加载。跨文连接：code-level-notes §5.1 明确把这份清单当作 OIA @omni/* 打包的直接模板（id 前缀、client 插件带面板、market/index.json 市场索引）。代价：插件形态意味着记忆生命周期绑在 DSH 的插件生命周期上——升级、禁用、换 Profile 都要跟着走，这与琥珀那种独立部署（Docker + 域名 + 数据库）是两种运维哲学。

治理三接口：纠正 / 抑制 / 时间限定

接口你的话术（README 原例）系统行为
纠正「这条记错了」；或随口改口「奶茶我戒了，现在改喝美式」按新值来；旧的那句在「TA的记忆」页用小字留着
抑制「别再提了」「别记了」不再提起、不再想起；那句话还在你电脑的档案里（数据保留，不再召回）
时间限定检索「昨天」「上周」「上个月」只在那几天里找；那几天没聊过就直说没有
词法 → 语义降级（首次打开时自动）先按关键词找，后台下完约 24 MB 的 bge-small-zh-v1.5（BAAI，MIT）后才按意思找

跨文连接：时间限定检索琥珀也有（memory_core/recall/date_period.py，昨天/上周…）——「时间」在社区项目里是一等查询维度，而不仅是排序里的 recency；词法兜底则呼应第 2 篇 rolling-memory：词法层不是残缺的语义层，而是可独立交付的底座，语义模型只是后装的增强。

洞察

抑制 ≠ 删除：一种可审计的沉默

「别再提了」保留数据、只撤召回——这让抑制是可逆的（想恢复只需取消抑制），也让「她记得但不说」成为一种可查询状态。代价是用户主权依赖界面：数据留在 ~/.xuyi/data 里，你必须相信「TA的记忆」页如实展示了被抑制的条目。替代方案是硬删除，干净但不可逆，且会连带毁掉上下文一致性（其他记忆引用了同一件事时会留下空洞）。

出处：xuyi-memory.md「她记得的你」「还有一些小事」。

纠正的脆弱点：README 自己承认，新旧两句几乎没有相同词时（先说「体重 120 斤」，后说「瘦到 110 了」）可能还会拿旧的。纠错命中依赖词面重叠——与词法兜底是同一个脆弱点，语义模型装上后会缓解，但「改口」的判定本身仍是词法触发的。

20 题盲测：方法论比分数更值钱

README 给出的评测方法（折叠在「怎么测的」里，值得逐条抄）：

  • 题先写：20 道题是测之前就写好的，续忆没有照着这些题改过代码；
  • 干净环境：三款插件各装在一个互不影响的环境里，读同一段聊天、问同样 20 个问题；
  • 判分客观：插件把带答案的那句原话交给 AI 就算找回；两道「嘴严」题要相关的话没被主动交给 AI 才算过；只看插件能不能翻出来，不看 AI 最后怎么措辞；
  • 素材自造：聊天是编的（两个多月、藏 20 件小事），没用任何人的真实聊天记录；
  • 时间与版本钉死：2026 年 11 月 11 日测的，三款插件都用当时公开发布的版本。

结果：续忆 16 / 某记忆插件 A 4 / 某记忆插件 B 13（20 题找回）——自报·未复现，这是项目自报的自建测试，题集、聊天与环境都由项目方设计，本系列未复现，外部效度有限。更值得注意的是失败 4 题被原文公开：体重 120 斤改到 110 斤没说「改成」、说过分手了又问女朋友叫什么、一句话里换掉周末计划、说过「别叫我宝宝」再问怎么叫你——每种都标注「还在改」。

批判

日记定稿 vs 记忆可纠错：两层叙事的张力

README 说日记「写完就不改了，跟真的日记一样」，而记忆层同时提供纠正与抑制。于是问题来了：当某条事实被纠正后，已经定稿的日记里若写了旧版本，以谁为准？日记是否随纠正更新，README 未作说明——本文不作推测。可以确定的是：这是一个不可变叙事层与可变事实层并存的架构，两者的一致性需要额外机制，而那套机制没有出现在文档里。

第二重批判：场景绑定。续忆的治理接口是通用的（纠正/抑制/检索都能移植），但它的宿主假设很窄——官方 QQ 机器人插件、群与私聊的分寸、11 个人设、晚上十点的日记。插件形态可携带，叙事层不可携带。这提示 OIA：治理接口要设计成宿主无关的纯数据操作，人设与叙事留给上层。

第四章 · Anima Brain

Anima Brain：可解释打分与证据链

Anima Brain（发行名 companion-engine，Alpha 0.6.0，MIT）是面向 AI 伴侣的持久记忆与情绪连续性 SDK：本地 SQLite + FTS5 运行，不需要 Anima 账号，也不需要 Convex 后端，包本身是 headless 的。它对本系列最直接的贡献是两个字：可解释。

grounded memory：证据链先于叙述

README 的能力表把 Grounded memory 拆成四件东西：原话（original messages）、有据事实（source-backed facts）、纠正（corrections）、关联证据（linked evidence）；code-level-notes §6 补上实现侧：evidence_index.py 与 note_evolution.py 让摘要必附引用证据、笔记演化留痕。写入策略可选 automatic / reviewed / off 三档——关闭事实写入仍然保存对话历史，README 强调「读、写、保留是三个独立的关注点」。

为什么（rationale）：quote validation 的措辞很关键——它「检查出处（provenance），不检查每个模型解释的真伪」。这把幻觉问题拆成两层：来源可追溯是机器可审计的（引用挂对没有），陈述为真仍需外部判断。代价是写入路径变重（每条摘要都要挂证据）；替代方案是让模型自评置信度——零证据链、不可审计，恰好是 grounded memory 要反对的做法。

一行排序公式，分数随结果返回

实读 src/companion_engine/retrieval.py：词法与向量两路先做 RRF 融合，再线性合成总分——

RRF(p) = 160 + p + 1 score = 0.6·relevance + 0.25·e−Δt/45 + 0.15·importance10

Δt 以天计：recency = math.exp(-max(0, now - when) / (45 * 86400))；relevance 有向量时取余弦，没有时退化为 rrf / max_rrf（元数据里标 relevance_basis: cosine | lexical_rank_proxy）。

数学直觉：Δt = 45 天时 e−1 ≈ 0.37，即一条记忆放满 45 天，时效项只剩约三成权重；90 天约 0.14。三项都在 [0, 1] 量纲上（importance 除以 10 归一），所以 0.6 的相关性主导排序，时效与重要性是同量纲的微调——这解释了为什么公式敢用固定权重：它的每一项都有语义，不是黑箱参数。可解释的另一面：结果里还直接带 "ranking": "0.6*relevance + 0.25*exp(-age_days/45) + 0.15*importance/10" 这个字符串与逐条 metadata，上层界面无需复述规则就能展示「为什么是这条」。跨文连接：RRF 的词法侧与余弦侧的取舍，和续忆「词法兜底、语义后装」是同一个降级思路；code-level-notes §6 建议 OIA 把 0.6/0.25/0.15 做成配置照搬进召回精排。替代方案：学习排序（Learning to Rank）可能更准，但需要训练数据、丢了分项语义——在「伴侣记忆」这种可解释性优先的场景里，线性公式反而是特性。代价：三个权重是拍出来的，且 when 的取值（事件日期 vs 最后强化时间）对老记忆的影响不亚于权重本身。

SQLite + FTS5：零依赖的 rationale

引擎本地跑在 SQLite + FTS5 上，无需账号与云后端；离线示例用合成数据、不发任何模型调用；可选 embeddings。为什么：单文件数据库可复制、可备份、可离线，FTS5 直接给词法路供数，与 RRF 的 lexical 侧天然对齐；替代方案是向量数据库 / 托管后端，能力更强但引入运维与依赖成本。代价与诚实边界（README「Status and license」原话）：本地存储不等于本地推理（配置的 provider 会收到提交的上下文）；owner id 只是命名空间、不是认证；情绪状态是虚构模拟、不是心理评估。

引用式摘要与情绪连续性（简述）：核心记忆与情节摘要都带引用（cited core and episode summaries），配合有界追问（bounded follow-up lookup）维持跨轮的连续感；情绪线（PAD / 张力衰减等）在官方 Brain Atlas 里有专门视图，但其定位已由 README 划清——模拟，不是评估。对 OIA 的启示：情绪可以是叙事状态，不能是诊断结论。

"""Shared waiting period for pending cards and future topic-summary review."""

from dataclasses import dataclass
from datetime import date, datetime, timedelta, timezone
import os

# Automatic approval stopped because settings or the day's source changed after
# extraction. Saving the draft in review clears it.
MANUAL_REVIEW = "manual_review_required"


@dataclass(frozen=True)
class ApprovalSettings:
    delay_hours: int = 48

    def __post_init__(self):
        if type(self.delay_hours) is not int or self.delay_hours<=0:
            raise ValueError('自动入库等待小时数必须为正整数')

    @classmethod
    def from_env(cls):
        try:
            return cls(int(os.environ.get('MEMORY_AUTO_APPROVE_AFTER_HOURS','48')))
        except (TypeError,ValueError):
            raise ValueError('MEMORY_AUTO_APPROVE_AFTER_HOURS 必须为正整数') from None

    @property
    def delay_days(self):
        # Counted in business days so a draft made a few minutes after one
        # daily run is not pushed back a whole extra day.
        return max(1, -(-self.delay_hours // 24))

# [示意性实现] 节奏注入 —— 依据 README：Profile 首个可用轮次；Procedure 第 1/6/11 轮，之后每 5 轮
def inject(turn: int, *, compaction_verified: bool) -> dict:
    procedure_due = turn in (1, 6, 11) or (turn > 11 and (turn - 11) % 5 == 0)
    return {
        "profile": turn == 1,                       # 用户偏好：首个可用轮次注入一次

第六章 · 延伸问题

延伸问题：等待期有没有下界

延伸问题

48 小时自动收录的等待时长，是否存在信息论意义上的最优下界？

理论分析：把人审漏斗看成一个假设检验：抽取器给出候选卡（假设），用户后续行为与对话是观测证据，收录 = 接受假设。等待期的收益来自「等待期间新增的对话可能确认或否证这张卡」——48 小时恰好覆盖两个业务日的夜间作业，让第二天的聊天成为第一天抽取的独立证据源；等待期越长，可累积证据越多，入库卡的查准率越高。等待期的成本有三项：其一，按 README 流程，pending 卡不入长期记忆库，等待期内对这类新事实的查全率为 0（用户今天说的规则，后天才能被召回）；其二，积压线性增长（ready_count/overdue 指标），人审负担挤占别的交互；其三，信息会过期——事件类记忆的时效半衰（参考 Anima 的 45 天尺度）意味着等待期本身就在消耗记忆的可用价值。因此最优等待期 w* 应当使「查准增益(w) + 证据累积(w)」与「查全损失(w) + 积压成本(w) + 时效损失(w)」相抵；若每类记忆的错误发现率随等待时间的边际增益递减，则存在一个由最少额外观测数决定的下界——低于它，人审与自动收录的差别在统计上不可分辨，等待就只是纯损失。

研究方向：① 按记忆类型差异化等待期——琥珀的归档规则已经按类型分档（规则/边界与高情感约 1 年、里程碑至少 1 年、稳定事实约半年、普通事件约 4 个月），把同一思想搬到审核端：规则与边界类错一次代价最高 → 长等待 + 必人审，事件类时效敏感 → 短等待 + 高自动率。② 自适应等待——用抽取置信度、实体冲突检测、后续对话中的独立确认次数动态调整 review_ready_at，而非固定 48。③ 用采纳数据反标错误率——琥珀已经在记录「真正被用上的记忆」而非只看是否被搜到（生命周期里的「被想起」环节），这批 stats 可以反过来估计各类型卡的错误发现率，从而把 w* 从理论下界拟合为经验曲线。④ 跨系统对照——MemoraX 的即时写回 + 影响披露、续忆的即时可纠错、琥珀的 48h 漏斗，恰好是「零等待 / 零等待可撤销 / 有等待」三档，可作为等待期实验的三个天然基线。

洞察

四个项目其实是四种「记忆供给策略」

MemoraX 推（节奏注入 1/6/11）、琥珀 拉（三路召回按句取卡）、续忆 推拉兼备（抑制/纠正后按需检索 + 词法兜底）、Anima 算（线性打分把排序责任压进公式）。治理上则对应：即时写回可披露、48h 人审、即时可撤销、可解释打分——OIA 不必发明新机制，把这四档按记忆类型分配即可。
