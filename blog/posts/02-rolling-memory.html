CHAPTER 01

verbatim 铁律：历史发生即记录

rolling-memory 的入库路径只做一件事——确定性清理：剥离协议外壳、去掉 <thinking> 块、去掉重复日志行。零 LLM、零向量、零网络请求（README §3 步骤 1/2）。它的全部激进性都藏在这个「不」字里：不改写、不压缩、不润色。

论证链：为什么「用模型改写对话」是错误复合

  1. 前提：能误解上下文的 agent，负责摘要的 LLM 同样会误读上下文——摘要不是「蒸馏」，而是一次新的解读。
  2. 复合：用一个可能幻觉的模型，去改写一段可能已被误解的对话，等于把两层不确定性叠乘在写入时发生，且方向不可逆（README §2.1 原文称之为 error compounding）。
  3. 不可恢复：一旦原对话被「摘要后丢弃」，真相永久丢失——后续任何修正都只能在二手转述上进行。
  4. 修正悖论：某些系统主张「代价高昂的显式迭代记忆修正」，但 README 立即反问：你怎么检测到错误？又怎么保证错误记忆在被你抓住之前不污染后续推理？
  5. 结论（铁律）：history happened as it happened——今天召回的段落与明年召回的段落逐字相同，证据链不可动摇。

经济学：读时省几百 token，写时赔一整轮

README §2.2 把账算得很直白：LLM 摘要唯一明显的好处，是抽取出来的笔记在读取时短几十到几百 token；而相对 自报·未复现 长上下文 harness 单轮 100k–400k token 的活跃上下文，这点收益微不足道。写入端却要先付「LLM 理解成本」：要么活动 agent 中途多跑一轮 100k–400k 的「保存记忆」工具调用，要么一个 sidecar LLM 把全上下文读一遍。而 host 模型本来就坐在那里、本来就擅长读、还知道当前问题是什么——所以零成本的确定性清理 + 按需交付原文，才是更便宜的工程选择。

符号论证与分工论证

工程查回的大多是字面锚：项目代号、函数名、配置键、错误串、端口、版本标签、日期、文件路径。README §2.3 指出密集向量靠把文本平滑进连续语义空间来桥接宽松同义词，代价是近乎相同的符号变得难以区分——err_code_4012 vs err_code_4013、端口 8008 vs 1828、v0.0.1 vs v0.0.2、2026-05-12 vs 2026-05-19 之间的 cosine 相似度 >0.98（README 论断）；静态 embedding 词表还难以容纳新造标识符，回填数万条历史轮次要下载模型或让 CPU 风扇狂转数分钟。更重要的是 coding harness 的语言环境：同一个模型、同一个代码库，输出结构良好、用词一致、少省略主语少歧义指代——这正好是词法-统计架构最舒服的主场（README §2.3 第 3 点）。

分工上（README §2.4）：前沿 LLM 已经在你面前，本地记忆工具不必再养一个后台小模型猜语义，它的职责是几十毫秒内交出高信息量的原文证据，把 100% 的语义推理留给 host agent。团队自陈曾用重量级 LLM 抽取 + 向量 + 知识图谱架构在 LoCoMo 拿到 92.79 分 自报·未复现——正是因为跑过重管线，才对它隐藏的 token 账单与入库延迟有切肤之痛。

洞察 INSIGHT

「错误复合」的可证伪表述

两条路线的差别不在摘要质量，而在错误是否可追溯：摘要把错误固化进唯一事实源（single source of truth 变成 single source of error），verbatim 把错误留在可回查、可比对、可追加的原文里。这是一条可以直接做对照实验的命题——同一批对话分别走「摘要入库」与「原文入库 + 事后检索」，统计下游推理被错误记忆污染的次数。

跨文连接：本系列第 1 篇腾讯云 L1 抽取同样规定「背景消息仅用于理解、严禁从中提取」——两者都在防写入期信息损失，一个靠提示词纪律，一个靠根本不改写。

批判 CRITIQUE

verbatim 的代价：存储/索引成本与零重叠查询

其一，成本只是被挪走了。原文全量入库意味着存储与索引规模随会话近似线性增长。README 的缓解手段是挂载本地文件只记录路径与字节偏移、按需就地读取（不把仓库复制进库），外加「任何时刻可从 vault 重建索引」的本地索引设计；但对话本体仍要全量落 SQLite，README §5 自陈百万级流式负载尚未测试。对个人开发者这通常不是问题，对它是。

其二，零重叠是结构性的。昵称 vs 正式名、省略主语、模糊指代——词法检索对这类查询无解，且不是调参能救的（量化见第五章）。替代方案：LLM 摘要路线（本系列第 1 篇）与 dense vector 路线都能提供语义桥；rolling 的立场是先把 verbatim 基线做牢，桥是第二步——这是一个刻意的工程取舍，而非对桥的否认。

CHAPTER 02

自信息权重：信息量即权重

评分内核的第一块砖是 RuneShannonBits(r)：按 Unicode 文块给单个码点一个先验香农信息量 H0(r)（源码注释：based on the effective symbol capacity of its Unicode script block）。没有词表、没有 IDF 统计、没有模型——只有分档常数。

数学直觉：分档值在说什么

  • 10 bit ≈ 5 个英文字母：10 ÷ 2 = 5——一个汉字承载的信息量约等于五个拉丁字母。中文日志天然比英文日志「每字符更贵」，这在跨语言语料里直接放大稀有词的相对权重。
  • 3.32 = log2(10)：一个十进制数字位的自信息，恰好是 23.32 ≈ 10 个等概率符号——分档值与信息论定义自洽。
  • 空白 = 0：分隔符不携带内容，缩进、换行、制表符刷屏不会稀释真正的内容词——这正是「抗日志重复刷屏」的第一道闸。
  • ASCII 标点 = 1.0：源码注释特意声明本函数是通用字符串熵原语，^、$ 等标点各计 1.0 bit，不为已退役的检索通道留特例。

文件头还有三个语义阈值常数：AtomicConceptEntropyBits = 8.0、SingleAlternationMaxBits = 4.5、OverStemmingDivergenceMaxBits = 11.5——后续折叠逻辑会把退化串压到 8.0 bit（原子概念）以下。

StringShannonBits：四种抑制

字符串自信息 = Σ 字符 bit，再叠加四种抑制（源码函数注释逐字列出）：

  1. 无载体清零：字符串中没有字母/数字 → 直接返回 0（if !hasAlnum { return 0 }）。纯符号噪声串不产生任何权重。
  2. 一阶马尔可夫重复阻尼：同一字符连续游程长度 k ≥ 3 时，游程第 k 位的贡献乘 0.25^(k-2)（由 powQuarter 位移快查，避免 math.Pow 开销）。前两位全额，第三位起按四分之一衰减。
  3. 滑窗串联重复折叠：对无空格的紧凑单 token（n ≥ 4），在周期 p ∈ 1..4 上检测 tandem 重复（stepStreamingTandem：命中 pMatch[p] == 2p 即锁定），重复占比 ≥ 0.60 时整体乘阻尼因子。
  4. 跨空格洪泛折叠：有空格、n ≥ 16 且 4·tandemTotal ≥ 3n（≥75% 载体字符被周期 1..4 的循环锁死，如 "a a a …"、"ab ab ab …"）时乘洪泛阻尼，把整串压到原子概念阈值 8.0 bit 以下，而正常多词自然语言句子不受影响（源码注释原话）。
H(s) = 0，若 s 中无字母/数字；否则 H(s) = [ Σr∈s I(r) · 0.25max(0, kr−2) ] · D(s)
kr 为该字符在其连续游程中的位置序号；k < 3 时指数取 0（不衰减）。D(s) 为下述串联/洪泛折叠因子。
H("aaaa") = 2.0 + 2.0 + 2.0·0.25 + 2.0·0.252 = 4.625 bit （对照无重复 "abcd" = 8.0 bit）
Dflood(s) = max(0.05, 1−ρ)2 · 0.25 · min(1, 16n)，其中 ρ = tandemTotaln；单 token 情形 ρ ≥ 0.60 时 D = max(0.05, 1−ρ)2 · 0.25
下限 0.05 保证阻尼永不归零；n > 64 的流式长串另有 0.04·(64/n) 的额外下压（与前者取 min）。
洞察 INSIGHT

权重不依赖冻结词表——这是「零成本」的真正含义

TF-IDF 需要分词器 + 全局文档频统计；静态 embedding 需要下载模型 + 回填历史。这里只有字符分档先验 + 局部重复阻尼，权重直接随当前 vault 的实际分布自适应（README §3 步骤 2a：adaptive self-information & burst-clone folding）。docs/code-level-notes.md §1.1 记录的借鉴要点正是：用「信息 bit 数」做检索权重与预算单位（query coverage 以 nats 计），比 TF-IDF 更抗日志重复刷屏——评分单位与预算单位同源，才能直接相加、直接比较。

批判 CRITIQUE

分档常数是先验，不是推导

10 / 7 / 4.2 / 3.32 / 2.0 / 1.0 / 0.5 这组数值在源码注释中只被解释为「Unicode 文块的有效符号容量」，未见推导；阻尼阈值（k ≥ 3、p ≤ 1..4、串联占比 0.60、洪泛占比 0.75、n ≥ 16、下限 0.05）同样是工程阈值。README §5.4 自陈当前评测集中于英文个人档案与长对话（约 104 量级记录），其他语言、重度 code-switching、百万级流式负载仍待测试 自报·未复现——在中文语料上「汉字 10 : 字母 2」这个 5:1 的比例是否最优，属于替代方案层面的开放问题：可做按语种缩放的分档表 + 配对消融来验证，而不是默认照搬。

CHAPTER 03

突发折叠与族权重：出现分布，而非出现次数

单字符 bit 解决「这个词多稀有」，还没解决「这个搭配被刷了多少次」。同一段日志在同一天被贴 100 遍，TF 会把它顶到榜首、淹掉稀有词。rolling 的解法是给每个词族（word family）算一个有效权重，其核心思想一句话：按出现分布打分，不按出现次数打分。

effDF = 1 + (df − 1) · clusters − 1df − 11/e · disp
weight = ln(1 + clusterN + 1effDF + 1)，disp = min(1, Hln(df))，其中 H = − Σi pi · ln pi
df < 2 时 disp = 0；df = 1 时 effDF 恒为 1。H 由 familyEntropy 以自然对数（nats）求和，pi = 伙伴计数 / 总计数。

数学直觉：三个量各管一件事

  • effDF（有效文档频）= 1 + 独立性折扣。基线是 1；(df−1) 是「若每次出现都独立」的上限贡献；((clusters − 1)/(df − 1))1/e 是独立性插值——clusters = 1（全部出现聚在同一时间簇，即同日突发）时该项为 0 → effDF = 1，权重不被 df 稀释；clusters = df（每个文档各自独立成簇）时该项为 1 → effDF = df，按独立事件全额衰减。指数取 1/e 而非 1，意味着聚簇早期（clusters 刚离开 1）折扣爬升很慢——轻微聚集几乎不扣分，完全聚集完全保值。
  • disp（伙伴离散度）= 熵占比。familyDispersion 的注释写得清楚：一个词族在 df 个文档里各自搭配不同伙伴时 H = ln(df)，disp 达到 1（独立事件极限）；伙伴计数超过 df 饱和于 1，因为「任何词族携带的有效事件数不可能多于它的文档数」。
  • weight = 对数压缩后的有效密度。effDF = 1 时取得最大值 ln(1 + (clusterN+1)/2)；effDF 增大则按 ln 衰减——对数既压住长尾刷屏，又保证权重恒为正、可加。

于是同一个公式的两侧行为截然相反：同日重复日志（burst）→ clusters 不涨 → effDF 卡在 1 → 权重保值；分散出现（dispersed）→ disp → 1、clusters → df → 按独立事件对数衰减。这正是 README §3 步骤 2a 所说「同一天反复粘贴的近重复日志被对数折叠，从而永不稀释稀有词」的公式化实现。

事件内饱和：burstFreeQuota = 3

词族层面之外，unit_relations.go 在事件内（intra-event）另给了一道饱和闸：burstFreeQuota = 3.0——同一事件内重复出现的前 3 次免费，之后按指数衰减：

satDecay = exp( − max(0, microOcc − 3) · e )
microOcc 为事件内微出现次数（由时间亲和度累加）；超过配额第 1 次即乘 exp(−e) ≈ 0.066，是断崖式硬饱和而非线性打折。

docs/code-level-notes.md §1.2 把这组常数总结为可移植的初版参数：常数 3 与 e——「前 3 次免费，第 4 次只剩 6.6%」。它的直觉是：重复第三次以内是证据的互相印证（endorsement），第四次起就是刷屏。

洞察 INSIGHT

为什么这套公式值得整体移植

BM25 的 idf 与饱和 tf 只有一个轴（次数），TF-IDF 也没有「时间簇」和「伙伴熵」这两个分布轴。familyEffectiveWeight 用 df × clusters × 伙伴熵 三个量把「刷屏」与「多次独立印证」区分开：刷屏保值（不进分母）、独立印证衰减（进分母）。docs/code-level-notes.md §1.2/§8 的结论是：OIA 的 @omni/memory-recall T0 层直接采用此权重模型，公式自实现、不搬代码——因为 rolling-memory 是 PolyForm Noncommercial。

跨文连接：与琥珀之心的「人审状态机」（第 4 篇）互补——那里用流程治理重复，这里用数学治理重复。

批判 CRITIQUE

结构常数与校准值的边界，要看源码注释怎么说

pipeline.go 对 transmissionPerHop = 1/e 明确标注 universal constant, not a calibrated threshold，但对 anchorConcentrationFloor（≈ e−1）、shellScatterFloor、cloneDampingKernel（≈ e−2）三个常数一律标注 [calibrated]，并写明「换成零假设噪声带的方案实测反而回退（composite 73.67→72.94）」。数值上都与 e 的幂重合，语义上却一个是推导、一个是拟合——移植者必须逐个查注释，不能因为长得像数学常数就当定理用。familyEffectiveWeight 里的 1/e 指数与 burstFreeQuota = 3.0 在所读片段中未见推导注释，应视作可调超参并做配对消融（README §5.3 自陈的调参纪律同样适用于此）。

CHAPTER 04

两跳扩散预算：1/e 透射率与注意力的经济学

直接命中只是种子。为了把「同实体 / 同事件」的邻接证据也捞出来，引擎从种子向外扩散：一跳（Hop1）、再一跳（Hop2），每跳都要交透射税，并受显式预算约束。这套设计的全部目的，docs/code-level-notes.md §1.4 说得干脆：防止相关但无用的证据淹没注入窗口。

transmissionPerHop = 1e ≈ 0.3679，Thop2 = 1e2 ≈ 0.1353，E(v) = T · E(seed) · m(b)min(H(seed), H(v))
源码注释：每跳 1 nat 惊异是投递包络的单位可通约公理（paper Theorem 4），局部槽核 exp(−(d−1)/e) 是它的几何级数，其和 Zlocal = 1/(1 − e−1/e)；扩散对多路径取 MAX 而非求和。
compBound = (1/e)2 · lex · ( 1 − exp( − lextotal ))
pipeline_select.go L346：结构补偿上界，与 base + structBound 一起构成 stage2 的剪枝判据（下界不够高即跳过该候选）。

架构洞察：预算是注意力预算，不是随便设的数

  • 两跳即截断。Hop1 透射 1/e ≈ 0.368，Hop2 透射 1/e² ≈ 0.135，Hop3 将只剩 ≈ 0.05——边际信息已低于「把它塞进上下文并重发一整轮」的成本。1/e 的几何衰减给了自然截断点，两跳是经济学选择而非拍脑袋常数。
  • 预算是软上限。DefaultHop1Expansions = 1024、DefaultHop2Expansions = 512，且源码注释明确：等能量种子组跨过预算边界时整组完整展开，因此预算是软上限；时间上界由被选种子的所有桥的倒排遍历工作量决定。
  • MAX 而非求和。多种子-桥路径到达同一邻居取最大能量——避免「多个弱路径叠加出一个假强候选」，这是与 RRF/求和式融合截然不同的取值哲学。
  • 能量与预算同单位。直接命中能量 EnergyMutualInfo：E(u) = I(u)，候选与查询共享原子的自信息和，以 nats 计（pipeline.go L71–72 注释）——与 entropy.go 的 bit 口径差一个 ln2 常数因子，不改排序。评分单位 = 预算单位 = 扩散能量单位，整条管线因此可以逐层比较。
洞察 INSIGHT

省轮次的机制，其实是「少注入垃圾」

扩散预算与 turn-elimination 是同一枚硬币的两面：预算挡住「相关但无用」的证据 → 注入窗口里只有高信息量原文 → 一次 recall 就能让 agent 定位坐标、不再盲搜 → 省掉一整轮 100k–400k 的上下文重发。信息量即权重（第二、三章）与跳数即预算（本章）共享同一个 nats 单位，才能闭环。

批判 CRITIQUE

上界不紧就会错杀，软预算就会超支

compBound 是上界而非真值：当 bound 不紧时，base + structBound < seedFloor 的剪枝可能跳过本该入选的候选（宁可错剪换速度）。同理，软预算意味着等能量组跨边界时会超出 1024/512——吞吐的最坏情形并不被常数封死。两者都是「速度优先」的取舍，移植到 OIA 时应把 seedFloor 与预算做成配置项并配对消融，而不是照抄默认值。

① RuneShannonBits：按 Unicode 文块给单字符分档

整个权重体系的地基。ASCII 快路径先判字母/数字/空白，非 ASCII 再判组合符、空白与文块分支（本节选省略假名/泰文等 4.2 分支的完整 case 列表）。返回值即该字符的先验自信息 H0(r)，单位 bit。

[源码原文] internal/text/entropy.go · L17–55（节选） 
// RuneShannonBits returns the intrinsic prior Shannon information content H_0(r) (in bits)
// of a single Unicode code point r based on the effective symbol capacity of its Unicode script block.
func RuneShannonBits(r rune) float64 {
	if r < 0x80 {
		if (r >= 'a' && r <= 'z') || (r >= 'A' && r <= 'Z') {
			return 2.0
		}
		if r >= '0' && r <= '9' {
			return 3.32
		}
		if unicode.IsSpace(r) || unicode.IsControl(r) {
			return 0.0
		}
		return 1.0
	}
	if unicode.Is(unicode.Mn, r) || unicode.Is(unicode.Mc, r) || unicode.Is(unicode.Me, r) {
		return 0.5
	}
	if unicode.IsSpace(r) || unicode.IsControl(r) || unicode.Is(unicode.Cf, r) {
		return 0.0
	}
	switch {
	case unicode.Is(unicode.Han, r):
		return 10.0
	case unicode.Is(unicode.Hangul, r):
		return 7.0
	// …（节选省略：Hiragana/Katakana/Thai/Lao/Khmer/Myanmar/Tibetan 分支 → 4.2）
	case unicode.IsDigit(r):
		return 3.32
	case unicode.IsLetter(r):
		return 2.0
	default:
		return 1.0
	}
}

② StringShannonBits：四种抑制的函数注释与主循环

注释即规格说明：无载体清零、一阶马尔可夫重复阻尼 0.25(k−2)、滑窗周期 p∈1..4 串联折叠、跨空格洪泛折叠。主循环里 runLen ≥ 3 && rb > 0 那三行是阻尼的全部实现；末尾两个分支决定用哪个折叠因子。

// StringShannonBits computes the total prior Shannon self-information (in bits) of a string,
// enforcing non-carrier zeroing (0.0 bits when no letter/digit is present), 1st-order Markov repetition
// damping (0.25^(k-2) for identical rune runs of length k >= 3), sliding-window period-p (p in 1..4)
// tandem-repeat collapse on compact single-token strings, and cross-space periodic flood collapse on
// long space-delimited repetition floods.
func StringShannonBits(s string) float64 {
	var bits float64
	hasAlnum, hasSpace := false, false
	var prevRune rune
	runLen := 0
	// …（节选省略：buf/ring/pMatch/tandem 等串联检测状态声明）
	for _, r := range s {
		skipCf, isSp, isAlnum, lowR, rb := classifyRuneShannonFast(r)
		if skipCf {
			continue
		}
		if isSp {
			hasSpace = true
		}
		if isAlnum {
			hasAlnum = true
			// …（节选省略：写入 buf 并推进 stepStreamingTandem）
		}
		if lowR == prevRune {
			runLen++
		} else {
			prevRune, runLen = lowR, 1
		}
		if runLen >= 3 && rb > 0 {
			rb *= powQuarter(runLen - 2)   // 0.25^(k-2)
		}
		bits += rb
	}
	if !hasAlnum {
		return 0                             // 抑制①：无载体清零
	}
	if !hasSpace && n >= 4 {
		bits *= fullStringTandemDamping(&buf, n, tandemTotal)     // 抑制③：单 token 串联折叠
	} else if hasSpace && n >= 16 && tandemTotal*4 >= n*3 {
		bits *= spacedPeriodicFloodDamping(n, tandemTotal)         // 抑制④：跨空格洪泛折叠
	}
	return bits
}

③ familyEffectiveWeight + familyDispersion + familyEntropy

突发折叠的核心三件套：有效文档频 effDF、伙伴离散度 disp、以及以自然对数求和的族熵 H。注意 indep := math.Pow((clusters-1)/d, 1/eulerNumber) 中的指数就是 1/e，与第四章的透射率共用同一个 eulerNumber 常量。

[源码原文] internal/core/cluster_state_aggregates.go · L50–102 
func familyEffectiveWeight(df, multiDocCount, clusters int, total, entropy float64, clusterN int) float64 {
	effDF := 1.0
	if df > 1 {
		if clusters < 1 {
			clusters = 1
		}
		if clusters > df {
			clusters = df
		}
		d := float64(df - 1)
		indep := math.Pow(float64(clusters-1)/d, 1/eulerNumber)   // 独立性插值，指数 = 1/e
		disp := 1.0
		if total > 0 || multiDocCount > 0 {
			disp = familyDispersion(df, entropy)
		}
		effDF = 1 + d*indep*disp
	}
	return math.Log1p((float64(clusterN) + 1) / (effDF + 1))        // ln(1 + (clusterN+1)/(effDF+1))
}

// familyDispersion is the partner-entropy share H/ln(df) of one family, referenced
// to its document count: a family whose df documents each name a different partner
// has H = ln(df) and reaches 1, the independent-event limit. Partner counts beyond
// df saturate at 1, since no family can carry more effective events than documents.
// A family with fewer than two documents carries no dispersion.
func familyDispersion(df int, entropy float64) float64 {
	if df < 2 {
		return 0
	}
	return math.Min(1, math.Max(0, entropy/math.Log(float64(df))))
}

func familyEntropy(keys []uint64, counts []int32) (total, entropy float64) {
	for _, c := range counts {
		total += float64(c)
	}
	if total <= 0 {
		return 0, 0
	}
	for i := range keys {
		p := float64(counts[i]) / total
		entropy -= p * math.Log(p)                    // H = −Σ p·ln p（nats）
	}
	return total, entropy
}

延伸问题 Q1

词法-向量混合权重 wvec 是否存在依赖查询语言 / 标识符密度的最优值？

理论分析：滚动记忆自报的融合实验给出一对看似矛盾的读数：wvec = 0.15 时 Main R@10 提升（76.72% → 78.42%，+1.70pp），而 wvec = 1.00 时 Hard 集反而受伤（41.93% → 38.68%，−3.25pp）自报·未复现。它说明两路分数分布不可比：词法分建立在自信息能量（nats）之上，向量分是余弦相似度，量纲、动态范围与方差都不同，线性混合的最优 w 本质上取决于两路分数的尺度比与方差比；而尺度比随语料的标识符密度（错误串、端口、版本号的出现频率）与语言（汉字 10 bit vs 字母 2 bit 的先验差）变化——因此不存在全局常数 w 的理论保证；Hard 集本身的官方 R@10 只有 52.43%，等权融合等于把词法分的权重全部让位给量纲不同的向量分，先在这里受伤并不奇怪。

研究方向：做按查询自信息熵自适应加权：高熵查询（含稀有标识符 / 错误串 / 精确日期）信词法——这正是「信息量即权重」先验的用武之地；低熵查询（口语化、零重叠风险高，如昵称与省略主语）提高向量权重。可把 w 写成查询熵的单调映射 w = f(H(query))，用配对消融（README §5 的调参纪律 + docs/code-level-notes.md §1.5 的题集 pin SHA-256、逐题 JSONL 复算）验证其相对固定 w 的增益；观测接口可直接复用第 4 篇琥珀之心三路召回的 stats 贯穿设计，逐查询记录路由决策与采纳结果。
